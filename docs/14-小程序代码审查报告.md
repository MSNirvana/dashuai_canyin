# 14 · 小程序代码审查报告（bug 清单）

> 2026-09-24。范围：`apps/mini/src`（Taro 4 微信小程序，约 11.6k 行 / 69 个文件）。
> 方法：按功能分块（创作流 / 合成流 / 实体与全局壳）逐文件细读，跨文件处对照服务端 `server/src/routes|services` 契约；
> **每条发现都回到源码原文复核过**（行号 + 代码片段为证），子代理报的疑点不成立的一律剔除。
> 本文只列「会出错的地方」，不含风格建议。

---

## 0. 结论

代码质量整体**高于一般小程序项目**：请求层有会话代次（`utils/session.ts`）、合成提交按档位加锁、列表有请求代次守卫、
错误态与空态刻意区分、`requestId` 幂等、路由编号有 `readRouteId` 校验。这些都是踩过坑之后补出来的，注释里留着事故记录。

但缺口集中在同一种形状上 —— **「失败路径上的二次失败没人兜底」**，分三类：

| 主题 | 形态 | 后果 | 条数 |
|---|---|---|---|
| A · 失败≠空态 | 加载失败被当成「没有数据」，页面渲染出可编辑的空表单 | **保存即清空原有数据** | 3 |
| B · 并发无守卫 | 两个来源各发一次请求，谁后到谁生效 | 跨店/跨分类数据串台 | 3 |
| C · 防线位置错 | 守卫放在 `await` 之后、清理只在固定时机跑一次 | 重复扣费 / 卡死 / 资源泄漏 | 8 |

**共 21 条**：P1 七条、P2 十四条。

## 1. P1（数据丢失 / 资损 / 核心功能不可用）

### P1-1 ★ 菜品编辑：加载失败后渲染空表单且可保存 ⇒ 清空该菜品全部图片与封面

**位置** `apps/mini/src/pages/dish/edit.tsx:85`（加载）、`:181-195`（提交）


### P1-4 ★ 调过色的用户看成片 ⇒ 永久假加载「正在生成整片精确预览…」

**位置** `apps/mini/src/pages/render/compose.tsx:388-402`、`:447`、`:1084`、`:1094-1099`


### P1-7 ★ 提交合成失败时提示被 `load()` 立刻抹掉（网络层失败完全静默）

**位置** `apps/mini/src/pages/render/compose.tsx:960-962`

## 2. P2（特定条件下出错 / 体验缺陷 / 误导性反馈）

### P2-1 创作列表：`load()` 无代次守卫 ⇒ 切店后列表显示别家店的创作
位置 `pages/creation/list.tsx:157-180`（无 generation guard）、`:182`（`useDidShow`）、`:190-196`（`currentStoreId` effect）、`:241-249`（归档后 `await load()`）。
两个并发触发源共用同一个无守卫的 `load`：旧门店的慢响应后到会整片覆盖新门店的列表；归档后重载与首屏加载乱序会让刚归档的条目短暂复现。
同文件 `creation/edit.tsx` 的 `loadDishesFor` 专门做了这个守卫并写明理由，此处遗漏。

### P2-2 菜品列表：带 `storeId` 进入时双请求竞态 ⇒ 列表是另一家店的菜
位置 `pages/dish/list.tsx:47-84`、`:86-89`、`:93-103`。`useDidShow` 先用旧 `currentStoreId` 发一次，
`paramStoreId` 同步改全局门店后又发一次，两者无守卫、无乱序保护。

### P2-3 菜品详情：无 `useDidShow` ⇒ 编辑保存返回后仍显示旧数据
位置 `pages/dish/detail.tsx:18`（仅 `[id, storeId]` 依赖）。编辑页保存后 `navigateBack`，详情页不重拉。
同类页面 `store/detail.tsx:58-61` 有 `useDidShow` 并注明「从编辑页返回时立即看到最新内容」，菜品这条链路漏了。

### P2-4 老板人设：把请求失败当成「没有记录」⇒ 空表单可保存，清空原人设
位置 `pages/persona/index.tsx:37-41`。
服务端 `routes/persona.ts:26` 对无记录返回的是 **200 + 三个 null**（走 then 分支），所以**进 catch 的必然是网络失败/500**。
注释「没记录属正常，给空值」前提就是错的。与 `dish/list.tsx:33-35` 里写下的项目教训（「失败必须与真没有数据长得不一样」）矛盾。

### P2-5 门店「设为默认」开关：新建时打开无效、编辑时关闭无效
位置 `pages/store/edit.tsx:176`（`isDefault: form.isDefault || undefined`，新建/编辑共用）。
服务端 `services/store.service.ts:70-88` `createStore` 用 `isDefault: isFirst` **完全没读 input.isDefault**；
`updateStore:105` 只处理 `input.isDefault === true`，`false`/`undefined` 一律忽略。
⇒ 已有门店者新建门店勾选「默认」保存后不是默认店；把默认店的开关关掉再保存仍是默认店。两种都是 UI 允许、结果与预期相反且无提示。

### P2-6 「按当前调色重新出片」按钮的判据丢了档位过滤
位置 `pages/render/compose.tsx:340`（`lastSuccess` 取任意档位第一条 SUCCESS）与 `:1671`（`{lastSuccess && grade === 'BASIC' && ...}`）。
注释原话是「只在已有 BASIC 成片、且当前仍选 BASIC 时出现」。只跑过 AI 档的用户切回 BASIC 就会看到这个按钮，
而 RECOLOR 的语义是复用上一版 BASIC 归一化缓存（`server/src/services/render.service.ts:433`）。

### P2-7 录音不随页面卸载终止 ⇒ 退出后麦克风继续采集并上传孤儿素材
位置 `pages/render/compose.tsx:526-530`（卸载只清 `colorPreviewTimer`，**没有** `recordingTimerRef`/`recorder.stop()`）、
`:823-855`（`recorder` 是 `Taro.getRecorderManager()` App 级单例；`:838-845` 的 `onStop` 在页面已卸载时仍会执行 `uploadCustomVoice`）。
⇒ 用户点了「开始录音」后直接返回上一页：录音持续到 60 秒上限，然后真实发起一次上传，服务端落库一条**没有任何提交会引用**的素材；用户还会疑惑「为什么还在录音」。

### P2-8 上传凭证只取一次且全程冻结 ⇒ 大文件长上传超期后必然失败
位置 `services/upload.ts:191`（单次 `/upload/sts`）、`:250-260`（`getAuthorization` 恒返回同一份凭证）、`:115-163`（`sliceUploadWithRetry` 的重试也用同一个 `cos` 实例）。
文件头声明支持「单文件最大 2GB / 分片上传」，而 2GB 在普通上行下动辄几十分钟 —— 一旦超过 `sts.expiredTime`，
后续每个分片都用过期凭证签名而 403，精心写的「同 key 续传」恰好在最需要它的场景系统性失效，桶里还会留碎片。

### P2-9 精确预览的客户端超时（90s）小于注释声明的服务端上限（120s）
位置 `services/render.ts:222-226`。注释写明动机是「服务端单步容许 120s，仍用默认 30s 会在暖机路径上误报超时」，实现却取 `90000`。
暖机路径真跑满 120s 时客户端先断开。代价有限（预览免费、重试命中缓存），但实现与自述契约不一致。

### P2-10 选图/选视频被用户取消，也弹「上传失败」
位置 `pages/dish/edit.tsx:134`、`:138`。`Taro.chooseImage/chooseMedia` 用户主动取消时同样 reject，此处 catch 不区分。
同项目 `store/edit.tsx:116-118` 与 `services/profile.ts::pickAndUploadAvatar`（返回 null 表示取消）都做对了，此处漏了。

### P2-11 上传过程中可删除图片，上传完成后被旧快照覆盖 ⇒ 刚删的图又回来
位置 `pages/dish/edit.tsx:134`（`const next = [...form.images]` 闭包快照，循环上传后 `set('images', refreshSort(next))` 整体覆盖）
与 `:140-141`（`removeImage/removeVideo` **不检查 `uploading`**）。反方向（上传中添加下一批）被 `uploading` 挡住了，唯独删除通道没挡。

### P2-12 个人资料：加载中可点保存 ⇒ 清空昵称
位置 `pages/profile/index.tsx:92-96`（`onSave` 只挡了重复提交 `saveLock`，**没挡 `loading`**；`nickname` 此时是初始空串）

### P2-13 门店切换器：请求失败被降级成空列表 ⇒ 误报「还没有门店」
位置 `components/store-switcher/index.tsx:34-42`。`loadStores(true).catch(() => [])` 把失败与「真的没有门店」混为一谈，

### P2-14 App 前台刷新只跑一次
位置 `app.tsx:13-21`。注释写「每次进前台刷新积分余额」，实现是 `useEffect(..., [])`，没有注册 `Taro.onAppShow`/`useDidShow`。

### P2-15 「取消生成」不释放创建锁，生成按钮最长 120 秒不可用
位置 `pages/creation/edit.tsx:504-527`（`createLockRef`/`creating` 只在 `onCreate` 的 `finally` 释放，而 `finally` 要等 `await runAuto(...)` 走完）

⇒ 点「取消生成」后表单恢复了，但「生成」按钮仍 loading/disabled 直到那个请求回来（典型 8~13s，故障通道最长 2 分钟）。与 cancel 的意图相悖。

### P2-16 分镜重试缺「服务端双保险」（与文案步骤不对称）
位置 `pages/creation/edit.tsx:414`（文案步骤：`!(await getCreation(id).catch(() => null))?.copyText`，读服务端兜底）
