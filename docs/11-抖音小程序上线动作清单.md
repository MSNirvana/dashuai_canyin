## 0. 先看结论

**技术上可行**：Taro 4 已经是「一码多端」的雏形——`@tarojs/plugin-platform-tt` 已装，`npm run build:tt` 脚本已存在，产物会落到 `dist/tt`。页面本体（React 组件、样式、业务逻辑）**基本可以复用**。

**但有三条链路在抖音端必须换实现，不能复用**：

| 链路 | 微信端现状 | 抖音端要变成 |
|---|---|---|
| 登录身份 | `wx.login` + `getPhoneNumber` → 微信 `jscode2session` + `getuserphonenumber` | `tt.login` → 抖音 `code2session`；手机号走 `encryptedData + iv`，服务端用 `session_key` 做 AES-128-CBC 解密 |
| 支付 | 微信支付 v3 JSAPI（`prepay_id` + RSA 签名，端上 `Taro.requestPayment`） | 抖音担保交易（服务端下单拿 `order_id + order_token`，端上 `tt.pay`，`service: 5`） |
| 素材上传 | `cos-wx-sdk-v5` 分片直传 | 该 SDK 内部依赖 `wx.*`，抖音跑不了 ⇒ 改预签名 URL + `Taro.uploadFile` |

**★★ 真正决定能不能上线的不是代码，是资质与合规**（第 1 节）。三件最容易卡住的事：ICP 备案、`工具-AI工具` 类目定向准入、**第三方算法备案材料**。

**★ 一个好消息**：语音合成用的火山引擎 TTS（`openspeech.bytedance.com`）**本身就是字节云的**——抖音端这条链路天然同源，不需要换供应商。

**★ 一个提醒**：`apps/mini/src/config.ts:7` 的 `IS_DOUYIN`、`:14` 的 `SUPPORT_WX_QUICK_LOGIN` 是**只有声明、没有任何调用点**的占位常量（`grep` 全仓只匹配到定义处）。别被它们误导成「已经适配过」。

## 1. 资质与合规（★ 长周期，第一天就该启动）

这一节的每一项都是**人工流程、周期以周计**，和写代码并行推进。代码做完了资质没过，一样上不了架。

### 1.1 主体必须是企业或个体工商户　✅ 已定：企业主体
个人主体在抖音端基本走不通：`工具-AI工具` 类目要求**定向准入申请**，且个人主体仅能调用第三方算法服务、需额外提交三份材料（见 1.4）。
★ 已确认走**企业主体** ⇒ 下面两项仍需逐条办掉。

- [ ] 抖音开放平台注册开发者账号 → 创建小程序 → 完成主体认证
- [ ] 确认小程序主体与域名备案主体、支付商户主体**三者一致**（平台会交叉校验）

### 1.2 ICP 备案（抖音侧单独一套）
- [ ] 在抖音开放平台控制台的 ICP 备案系统提交：企业资质、域名信息、负责人信息、法人核验
- [ ] 周期约 3~7 个工作日（管局）+ 平台初审 1~6 个工作日
- [ ] ★ 注意：**这是「小程序备案」，与微信端那套是分开的**，同一主体在不同平台要分别办理
- [ ] ★ 已上线小程序**每年 3 月 31 日前要更新备案**，逾期会下架/停更 —— 排进年度日历
- [ ] 域名现状可复用：`api.dspcz.top` 已上 HTTPS（LE，2026-12-20 到期），满足「必须 HTTPS、禁 IP/localhost/泛域名」

### 1.3 类目与定向准入
- [ ] 「工具 - AI 工具」属**定向准入**，需先提内测申请（周期约 1~2 个工作日，但可能反复）
- [ ] 每个小程序最多 5 个服务类目，**一个月最多改 5 次** ⇒ 一次想清楚再提交
- [ ] 类目必须与实际功能严格匹配，否则以「类目不符/超范围经营」驳回

### 1.4 ★★ 算法备案材料（最大的不确定项）
规则口径是：

- **自研 AI 能力** ⇒ 提交自己的《互联网信息服务算法备案》（算法类型含「生成合成类(深度合成)」）
- **调用第三方算法服务** ⇒ 提交三份：① 第三方的算法备案**截图**（类型为「生成合成类」）② 第三方的备案**公示内容** ③ 《小程序主体与三方算法服务方合同协议》公示内容（须含开发者主体名、购买服务信息）

**⚠ 对本项目的具体风险**：我们的 AI 走的是自建网关 + 第三方中转（`tokenbox.you`）。中转服务商**通常不持有**「生成合成类」算法备案。所以：

- [ ] **先确认**：tokenbox 能否出具算法备案号与公示页？合同/服务协议能否公示？
- [ ] 拿不到 ⇒ 只有两条路：**(a)** 换成有备案的算法供应商（如已备案的大模型厂商直连）；**(b)** 自己以主体身份去 beian.cac.gov.cn 办「生成合成类」算法备案（周期长、材料重）
- [ ] ★ 这条也会反过来卡住微信端 —— 记忆里「生成合成类算法备案未办」本来就是未决项，抖音端把它从「应该办」升级成「不办上不了架」

★★ **2026-09-23 核实补充 —— 抖音平台实际要什么**（官方社区帖口径）：

- 平台要的是 **2 张截图**：① `beian.cac.gov.cn` 备案**查询结果页**（**状态须为「正常」**）；
  ② **算法公示内容**图片。**另加**合作协议，含 **4 个要素**：【小程序主体】【算法及应用名称】【备案编号】【小程序 appid】。
  ★ 平台提供合作协议模板，按模板开最保险。
- ★★ **AI 相关小程序在「小程序备案」这一步就要提交算法备案材料** —— 不只是类目资质那一步。
- ★ **时限**：首次算法备案应在**提供服务之日起 10 个工作日内**办理 ⇒「先上线后补」本身即违规，
  且平台在「备案」「类目资质」两步都会卡它。
- ★ 若改用**字节自家模型产品（豆包/火山）**，另需双方合同证明合作关系 —— 我们已在用火山 TTS，这条可顺带解决。

### 1.5 生成合成内容标识（强制国标）
《人工智能生成合成内容标识办法》2025-09-01 已施行，配套 GB 45438—2025：

- [ ] **显式标识**：成片画面要有用户可明显感知的「AI 生成」标识（角标/水印），且**下载导出后仍必须带标识**
- [ ] **隐式标识**：在成片文件元数据里写入生成合成属性、服务提供者名称/编码、内容编号
- [ ] 抖音审核会看「内容展示层面能否看到标识」，不只是后台勾选
- [ ] ★ 本项目当前**成片无 AI 生成标识**（记忆里的未决项）⇒ 这块要真做，不能只写文档

### 1.6 ★★ 餐饮 AIGC 的红线（产品语义层面的雷）
抖音生活服务《AIGC 创作规范》对**餐饮**类目有明确禁止项：

> 不得使用 AI 生成**不存在的餐品与套餐内容**；不得用 AIGC **夸大菜品分量**；不得用 AI 生成的**虚假环境替代实际就餐环境**。

- [ ] **复核「AI 生成封面」的产品语义**：如果它会凭空生成不存在的菜品/门店环境图，**这是直接踩线**，需要改成「只用商家上传的真实素材做加工」，或强制在封面上打 AI 标识并约束生成范围
- [ ] 本地打底 / 剪辑 / 配音 / 字幕这些**基于真实素材的加工**不在禁止范围内（规范针对的是「虚构商品与场景」）
- [ ] 文案侧：不得夸大分量、规格、效果，不得承诺无法兑现的服务

### 1.7 内容安全
- [ ] 用户输入（备注、关键字）与 AI 输出（文案、字幕）**两侧都要接内容安全校验**
- [ ] 抖音有对应能力（等价于微信 `msgSecCheck`），需申请权限并接入
- [ ] 需要有投诉举报入口

## 3. 工程改造 · 服务端（`server`）

### 3.1 抖音登录分支
- [ ] 新增：`code` → `POST https://developer.toutiao.com/api/apps/v2/jscode2session`（参数 `appid / secret / code`）→ 拿 `session_key / openid / unionid`
- [ ] 手机号：抖音是 `open-type='getPhoneNumber'` 返回 `encryptedData + iv`，服务端用 `session_key` 做 **AES-128-CBC（PKCS#7）** 解密得到 `purePhoneNumber`
      ★ 与微信不同：微信是拿 `phoneCode` **再调一次接口**直查，抖音是**本地解密**
      ★ 必须校验解密结果的 `watermark.appid` 是否为本小程序（防伪造）
- [ ] 现有实现可参考：`server/src/auth/wechat.ts:89`（jscode2session）、`:129`（getuserphonenumber）、`server/src/auth/auth.service.ts:69-92`（`loginByWechat`）
- [ ] **兜底路径已具备**：短信验证码登录 `auth.service.ts:105` `loginByPhone` 与 `server/src/routes/auth.ts:14,39` 与端无关，抖音端可直接复用 ⇒ 建议**抖音首版就用短信登录**，把抖音登录降级为后续增强

★★ **纠正（2026-09-23 核实平台规范；这条覆盖上面「首版只用短信登录、把抖音登录降级」的建议）**：

抖音《小程序运营规范》**10.6.1**：「小程序内存在账号体系时，**必须提供抖音授权登录**，且满足平台交互规范」。
⇒ **抖音端不能只做短信登录**，`tt.login` 是**必需项**，不是可选项。
⇒ 但**短信兜底仍要保留**：**10.6.3** 禁止「以第三方注册为由拒绝用户使用小程序」，即不能强制绑定抖音。
⇒ 另注：抖音手机号走 `open-type='getPhoneNumber'` 返回 `encryptedData + iv`，服务端用 `session_key` 做 AES 解密
（与微信「拿 phoneCode 再调一次接口直查」不同）。

### 3.2 身份表结构（★ 建议这次一并改对）
现状：`server/prisma/schema.prisma:17-18` 只有 `wechatOpenid` / `wechatUnionid` 两列。

- [ ] 涉及 schema 变更 ⇒ 部署要走 `deploy/db-baseline.sh` + `deploy.sh` 那条线（本项目既有约定）

### 3.3 支付抽象
现状：`server/src/lib/wxpay.ts` 全自研微信支付 v3（`:151` 下单、`:110` 签名、`:193` 关单、`:250` 查单），`server/src/services/order.service.ts:215,263` 下单时**强制要求商户有 `wechatOpenid`**（`:214,262` 抛 `NoOpenidError`）。

- [ ] 加抽象：`paymentProvider = wechat | douyin`，暴露 `createOrder / handleNotify / queryOrder` 三个方法
- [ ] 抖音侧要走**担保交易**接入：开通支付能力（企业担保交易）、**进件**（企业版/普通版二选一）、预下单扩展点、回调地址配置、公私钥上传、`order_id + order_token` 签发

## 6. 工作量与最不确定的三个点

**相对确定的部分**（工程量可估）：
- 配置与构建参数化：小
- 端差异 adapter + 各 API 适配：中等（调用点集中在 10 个文件左右）
- 抖音登录分支：中等

- 抖音担保支付：**大**（且强依赖进件审批）

**最不确定的三个点（建议先各花半天验证，再排期）**：
1. **tokenbox 能不能出具「生成合成类」算法备案材料** —— 拿不到就得换算法供应商或自办备案，这条能直接决定项目成立与否
2. **tdesign-miniprogram 在抖音端能不能正常解析** —— 解析不了要换组件方案，影响面覆盖全站 UI
3. **餐饮 AIGC 红线对「AI 生成封面」的判定** —— 如果封面被认定为「虚构餐品/环境」，这个功能在抖音端要么下线要么大改
