# 12 · 多端架构约定（微信 / 抖音 / 未来第三端）

> 2026-09-23 定。触发背景：抖音小程序要上，且**要做在线收款**、主体为**企业**。
> 本文回答一个问题：**多端要不要把代码隔离开？**
>
> **结论：一套仓库、一套源码基线，差异只收敛到一条显式的「适配缝」。**
> 不建第二个仓库，也不在页面里散写 `if (IS_DOUYIN)`。

---

## 1. 为什么不是「两个仓库 / 两套代码」

先看四种方案的代价：

| 方案 | 隔离程度 | 「一方升级另一方」的代价 | 判断 |
|---|---|---|---|
| A 完全共用，差异散写在业务代码里 | 无隔离 | 低（但代码会腐化成一屏 `if`） | ✗ 半年后不可维护 |
| B **一套基线 + 显式适配缝** | 差异隔离 | **≈0**（见 §4） | ✅ **采用** |
| C 两个仓库 / 两套代码 | 全隔离 | 每次改动都要人工同步两边，**且没有任何机制提醒另一端也要改** | ✗ 必然漂移 |
| D monorepo 里物理分两个 app 包 | 全隔离 | 同 C（只是放在一起） | ✗ 同 C |

**C/D 的问题不在于「麻烦」，而在于它把一个可以被编译器检查的问题，变成了靠人记性的问题。**
典型漂移：微信端修好的 bug 抖音端还在；一次安全修复只打了一半；两端 UI 悄悄长歪；平台合规改动（备案号、AI 标识）漏改一端。

**D 尤其要警惕**：把代码放到同一仓库的两个包，会给人「已经统一了」的错觉，但两个包之间没有任何共享约束，时间一长就是两个仓库。

---

## 2. 本项目的事实依据

排查（只读）结论：**两端差异其实很小，且高度集中**。

| 层 | 现状 | 平台耦合 |
|---|---|---|
| 页面 / 组件 / 样式 | `apps/mini/src/pages/**`、`components/**` | **零**（纯 React + Taro 抹平后的 API） |
| 业务逻辑 / 服务调用 | `services/*.ts`（除 upload） | **零**（都走 `services/request.ts` 的 `http`） |
| 平台适配面 | 登录、支付、上传、录音、选文件 | **全部耦合都在这里，约 5 处** |
| 服务端 | `server/src/**` | 仅 `auth/wechat.ts`、`lib/wxpay.ts`、`order.service.ts` 的 `NoOpenidError` |

- 端侧耦合点：`services/upload.ts:17`（`cos-wx-sdk-v5`）、`pages/mine/index.tsx`（`Taro.login` / `getPhoneNumber`）、`pages/recharge/index.tsx`（`Taro.requestPayment`）、`pages/render/compose.tsx`（`chooseMessageFile` / `getRecorderManager`）。
- 全仓 `grep toutiao|douyin|bytedance` **只命中火山 TTS 域名** ⇒ 除了上面这几处，没有任何地方碰过字节。
- ★ `src/config.ts:7,14` 的 `IS_DOUYIN` / `SUPPORT_WX_QUICK_LOGIN` **只有声明、没有调用点** —— 是「假适配」残留，不代表已适配。

**结论：为 10% 的差异复制 100% 的代码，是负收益。**
（配合 `docs/11-抖音小程序上线动作清单.md`：能复用的是页面，不能复用的只有登录/支付/上传三条链路。）

## 3. 三层职责（哪些共用、哪些分叉）

```
L0 平台无关层   ── 共用，唯一真源（≈90%）
     pages/ components/ styles/ hooks/ utils/ services/(除平台能力)
L1 平台适配层   ── ★ 唯一允许分叉的地方
     platform/{types,weapp,tt,index}.ts      端侧
     auth/provider + payment/provider        服务端
L2 配置与凭据层 ── 天然分开（本来就该分开）
     project.config.json(微信) / project.tt.json(抖音)
     .env(端上烘焙的 appid / baseUrl / 平台标识)
     服务端 WX_* / TT_*
```

### 3.1 L1 端侧形态

```ts
// apps/mini/src/platform/types.ts —— 契约（唯一真源）
export type PlatformFeature = 'quickLogin' | 'chatFile' | 'record' | 'subscribeMessage'

export interface PlatformAdapter {
  login(): Promise<{ code: string }>
  getPhone(evt: unknown): Promise<{ phoneCode?: string; encryptedData?: string; iv?: string }>
  pay(order: PayOrderInput): Promise<void>
  uploadFile(input: UploadInput): Promise<{ key: string }>
  chooseChatFile(): Promise<string | null>   // 抖音端无此能力 ⇒ 返回 null
  supports(f: PlatformFeature): boolean       // 页面据此隐藏入口，而不是自己判断平台
}

// apps/mini/src/platform/index.ts —— 唯一的平台选择点
import { IS_DOUYIN } from '../config'
import { weappAdapter } from './weapp'
import { ttAdapter } from './tt'
export const platform: PlatformAdapter = IS_DOUYIN ? ttAdapter : weappAdapter
```

页面从此只写 `platform.pay(...)` / `platform.supports('chatFile')`。

### 3.2 L1 服务端形态

```ts
// server/src/payment/provider.ts
export interface PaymentProvider {
  readonly kind: 'wechat' | 'douyin'
  createOrder(input: CreateOrderInput): Promise<ClientPayParams>   // 给端上的支付参数
  handleNotify(raw: Buffer, headers: IncomingHttpHeaders): Promise<NotifyResult>
  queryOrder(outTradeNo: string): Promise<OrderState>
}
// server/src/payment/index.ts
export function paymentProviderFor(p: PlatformKind): PaymentProvider
```

- 现有 `lib/wxpay.ts` **收敛成 `wechat` 实现**，不改行为。
- `auth/wechat.ts` 同理收敛成 `AuthProvider` 的 wechat 实现；抖音登录是 douyin 实现。
- ★ 必须改的一处语义：`order.service.ts:214,262` 现在**硬要求商户有 `wechatOpenid`**（否则抛 `NoOpenidError`）。要改成「按 provider 解析当前商户的支付身份」，否则抖音用户永远下不了单。

## 4. 「一方升级，另一方怎么办」——逐情形回答

| 升级发生在 | 方案 B（一套基线 + 适配缝） | 方案 C（两个仓库） |
|---|---|---|
| **L0 平台无关层**（UI、业务规则、bug 修复） | **改一次 ⇒ 两端同步** | 必须改两次，无提醒 ⇒ 必然漏 |
| **L1 适配层**（某端平台规则变了，如微信支付加参数） | 只改**那一份**实现，另端零风险 | 平手 |
| **新增平台能力**（如「分享」） | 接口加方法 ⇒ **TS 编译期强制两端都实现**，漏一端编译不过 | 改两次，漏一端**只有线上炸了才发现** |
| **依赖 / 安全升级** | 一次到位 | 打一半，风险翻倍 |
| **平台合规改动**（备案号、AI 标识、内容安全） | 一处 | 两处，漏一处 = 一端被下架 |

**只有第三行是「两端各写一次」，而且这一格由类型系统兜底。** 其余全部是「改一次两端受益」。
这就是为什么"共用一套 + 内部隔离"不是妥协，而是**同时拿到「隔离」和「自动同步」两件事**。

## 5. 红线（让「共用」不腐化）

1. **`IS_DOUYIN` / `IS_WEAPP` / `process.env.TARO_ENV` 只允许出现在 `src/platform/**` 与 `src/config.ts`。**
   页面、组件、hooks、services 里出现平台判断 ⇒ 视为 bug。
2. **平台能力先加接口、再加实现。** 禁止在页面里直接调 `Taro.requestPayment` / `Taro.login`。
3. **为抖音临时改动的公共代码，必须能通过开关回到微信端原行为。**
   ★ 判据：如果一次改动让微信端行为也变了，而它只是为了抖音 —— 那它不该这么写。
4. **长期并存的分支 = 分叉，禁止。** 抖音端上线晚、功能少，用「平台能力开关」关掉功能，
   不是开一条长期分支。任何存活超过一次发版的特性分支都要合并或删除。
5. **每加一个端差异，都要回答：微信端这条路径还通吗？** 微信端必须能被独立回归。

---

## 6. 真正该「物理分开」的东西（避免误解为反对一切分离）

| 分开的东西 | 为什么 |
|---|---|
| 构建产物 `dist/weapp` vs `dist/tt` | 本来就分开（`outputRoot: dist/${TARO_ENV}`） |
| `project.config.json` / `project.tt.json` | 两个 appid 必须并存，不能互相污染 |
| 端上 `.env`（烘焙进包的 appid / baseUrl / 平台标识） | 构建期常量，按端各一份 |
| 服务端凭据 `WX_*` / `TT_*` | 密钥天然分开 |
| **源码基线** | ★ **一份**，不分 |

## 7. 落地顺序（★ 第 2 步单独提交，且微信端必须零行为变化）

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | 落本文档 | 约定可引用 |
| 2 | **只抽骨架**：建 `src/platform/**`，实现**全部转发到现有代码**，页面改调 `platform.*` | ★ **微信端零行为变化**（这是「共用可行」的可证伪前提） |
| 3 | 服务端 `PaymentProvider` + `AuthProvider` 抽象，`wxpay.ts`/`wechat.ts` 收敛进去；改掉 `NoOpenidError` 语义 | 微信支付全链路回归通过；走 `db-baseline.sh` + `deploy.sh` 那条线（涉及 schema） |
| 4 | 身份表拆分：`merchant_identity(platform, openid, unionid)`，复用 `upsertMerchantByPhone` | 同手机号两端登录落到同一 merchant |
| 5 | 抖音实现（填空）：`tt.login`、手机号 AES 解密、担保交易、预签名上传 | 见 `docs/11-抖音小程序上线动作清单.md` §4 逐链路验收 |

★ **顺序不能倒**：先抽象再实现，抖音端接入就是「填空」；反过来先写抖音实现，就会把抖音的形态反向污染进公共代码。

## 7.1 已落地（2026-09-23 · 第 2 步）· 目录与守卫

```
apps/mini/src/platform/
  types.ts         契约：PlatformAdapter / capabilities / 参数类型
  impl.weapp.ts    微信实现（原样转发到现有代码，未改任何行为）
  impl.tt.ts       抖音实现（★ 骨架：login 转发；pay 未接入 ⇒ 明确抛错）
  impl.ts          兜底（仅为满足 tsc 解析；一旦被解析到就抛错，防止静默退化）
  index.ts         唯一入口：`platform`
```

**隔离机制**：`index.ts` 里写的是**不带后缀**的 `./impl`。Taro 的 `MultiPlatformPlugin`
（`@tarojs/runner-utils` 的 `resolveMainFilePath`，读 `process.env.TARO_ENV`）会把它解析成
`impl.weapp.ts` / `impl.tt.ts` ⇒ **另一端那份根本不会进入本端产物**。

**两条守卫（都已接进构建链）**：

| 守卫 | 位置 | 拦什么 |
|---|---|---|
| 产物级 · 跨端隔离 | `scripts/verify-weapp-dist.mjs` §7 | 微信产物里出现抖音端代码（金丝雀）；或适配层退化成兜底文件 |
| 源码级 · 边界 | `scripts/check-platform-boundary.mjs` | 平台判断写到 `src/platform/**` 与 `config.ts` 之外（红线 1） |

★ 金丝雀 `platform-impl-canary:tt` 刻意被插值进抖音实现的**运行时错误消息**里：
只有插进「可达的字符串」，压缩器才不会把它当死代码删掉 —— 否则「产物里没有它」这句话毫无意义。

**已验证（可复核）**：

- `npm run build:weapp:dev` → 自检通过：主包 **1.39MB / 2MB**（余量 620KB）、组件引用 ✓、tslib ✓、跨端隔离 ✓。
- **断言非空验证**：把金丝雀注入 `dist/weapp/common.js` 后重跑自检 → **如实失败（rc=1）**，随后恢复。
  （不做这一步，就无法排除「断言永远不会红」这种假绿。）
- **反向验证**：`npm run build:tt` 编译通过，且 `dist/tt/common.js` 里**确实有**金丝雀
  ⇒ 证明 `impl.tt.ts` 被正确解析、且金丝雀能存活 —— 微信侧那个「没有」才有意义。
- 两个被改动的页面文案仍在微信包内（`check-dist-strings.py` 四条全 HIT）。

**这一步有意没做（避免猜签名）**：

- **素材上传未进契约**：抖音要用预签名 URL + `Taro.uploadFile`，与微信的 COS 分片直传形态不同，
  等抖音方案定了再冻结签名。★ 后果已实测：**当前 `dist/tt` 里仍含 `cos-wx-sdk-v5`**
  ⇒ 抖音包在真机上跑不了上传，**尚不可发**。
- 录音 / 从聊天选文件仍未迁（待迁移清单由 `verify:boundary` 打印，当前 4 处）。
