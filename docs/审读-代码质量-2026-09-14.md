## 摘要：结论

**当前代码不能直接发体验版。**

不是因为架构差——实际上账务的两阶段扣费、原子抢锁、租户隔离主干、支付验签都做得相当扎实，属于「认真做过」的水准。问题在于存在 **7 个 P0，其中 3 个会让体验版根本发不出去或一打开就废**：

1. 一条请求就能把整个后端进程打死（**已实测复现**）
2. 小程序主包 3.38MB，超过微信 2MB 上限，**上传就会被拒**
3. 产物里内嵌着 `http://127.0.0.1:3000`，真机所有请求打向手机本机
4. AI 档在没有 ChatCut 授权时 100% 失败，而默认档就是 AI 档
5. 赠积分到期清零的代码写完了但**从来没被调用过**，且赠积分优先扣减 → 持续资损

另外有两个结论会改变之前的计划，见第六节。

## 一、P0 问题（阻断发布 / 安全）

### P0-1 一条请求即可打死后端进程 ✅实测 ✅**已修复（2026-09-14）**

| 项 | 内容 |
|---|---|
| 位置 | 精确为 **3 个端点**：<br>`server/src/routes/stores.ts:46`（`GET /:id`）← **已实测复现**<br>`server/src/routes/stores.ts:27`（`GET /`）<br>`server/src/routes/creations.ts:50`（`GET /`） |
| 成因 | 这 3 个 handler **没有 try/catch**，而 handler 内直接 `BigInt(req.params.id)`。参数传非数字时 `BigInt()` 抛错，Express 4 不会接管 async handler 的 Promise rejection，全项目**没有任何** `unhandledRejection` / `uncaughtException` 兜底 → 进程退出 |
| 后果 | 任意登录用户发一条 `GET /api/v1/stores/abc`，进程退出，**全部在线用户断开**。反复发即是持续 DoS |

**崩点范围已经用脚本扫全**：全目录 16 个路由文件、约 160 个 handler 里，只有上述 3 个「无 try/catch 且有 await」——所以这是个**三行就能修死**的问题，不要被下面那句吓到。

> 附带发现（P2，非崩溃）：`BigInt(req.params.*)` 这种裸解析全项目共 **48 处**，分布在 8 个路由文件。除上述 3 处外其余都被 try/catch 兜住了，不会崩，但会**返回 500「查询失败」而不是 400「参数错误」**——状态码和文案都是错的。正确做法是把路径参数统一收敛到一个 `z.coerce.bigint()` 校验器，48 处一起换掉。

实测证据：

```
$. GET /api/v1/stores/abc   (带有效 access token)
→ fetch failed（连接断开）

服务端 stderr：
/Users/.../server/src/routes/stores.ts:47
  const store = await storeSvc.getStore(prisma, req.merchantId!, BigInt(req.params.id))
                                                                 ^
SyntaxError: Cannot convert abc to a BigInt
Node.js v22.22.2          ← 打印版本号即进程已退出
```

**修复**：三件事一起做才彻底——① 路径参数统一改 `z.coerce.bigint()` 校验；② 加 async 错误包装器（或统一 try/catch）；③ `process.on('unhandledRejection')` 兜底并记录，别让进程死。

### P0-5 AI 档在未配 ChatCut 时 100% 失败；本地配音字幕管线是死代码 ✅代码核实

这是本次审读**影响面最大**的一条，因为它直接决定「能不能真实合成视频」这个目标。

代码事实链：

```
render.service.ts:266  grade 默认推导 → input.aiMode === false ? 'BASIC' : 'AI'   ← 默认就是 AI 档
render.service.ts:267  aiMode = grade !== 'BASIC'                                  ← AI 档 → aiMode = true

worker.ts:125  if (p.aiMode && chatCutConfigured())  { processChatCutTask(); return }  ← 走 ChatCut
worker.ts:129  if (p.aiMode && !chatCutConfigured()) { throw 'AI 档需要先完成 ChatCut MCP 授权和工具映射' }
worker.ts:196  if (aiMode) { await applyAiSynthesis(...) }   ← 本地 TTS + 字幕管线
```

推演可达性：

| 场景 | 结果 |
|---|---|
| aiMode=true 且配了 ChatCut | 走 125 行，直接 return，**到不了 196** |
| aiMode=true 且**没配** ChatCut | 130 行抛错，**到不了 196** |
| aiMode=false（显式 BASIC） | 196 行的 `if (aiMode)` 为 false，**跳过** |

**结论：`applyAiSynthesis`（本地配音+字幕）在任何路径下都不可达，是死代码。**

而当前配置状态：`server/.env` 里**零条** `CHATCUT_*` 配置，我写的 `deploy/env.server.template` 里同样一条都没有。所以部署上去后：
- **AI 档（默认档）每一次合成都会抛错失败**（钱会退回，但用户看到的是「合成失败」）
- **只有显式选「基础生成」档才能出片**（纯粗剪拼接 + 调色，无配音无字幕）

好消息是小程序端 `compose.tsx:46` 的默认档位是 `BASIC`，所以「能真实合成视频」这个目标**在基础档下是可达的**。

**修复方向（选一）**：
- 短期：接受只开放 BASIC 档，把小程序里 AI/PREMIUM 档位先隐藏或标注「即将开放」
- 长期：把 129-131 行的 throw 改成降级到本地管线（`applyAiSynthesis` 已经写好了，只是够不到），或在真机验收前把 ChatCut 授权配好

## 五、已核实「没有问题」的部分

这些是我逐条确认过的，**不用再花时间**：

**账务与支付**
- 幂等索引真实存在：`bean_ledger(merchant_id,biz_type,request_id,type)`、`bean_reservation`、`business_request`、`ai_call_log`（migration `20260909153000`）
- 原子扣减成立：`lockAccount` 用 `SELECT … FOR UPDATE`，三个动作的「读→算→写」都在锁后同一事务内，**无先读后写**
- 余额不可为负，`amount<=0n` 三处拒绝；赠积分优先分配逻辑正确
- 支付回调校验完整：appid + mchid + 金额一致 + 强制 CNY + ±300s 时间窗 + GCM 标签。**不存在「客户端说支付成功就发权益」的路径**，权益只经 `markOrderPaid`
- 订单终态 CAS 成立（`updateMany + claimed.count===0`），重复回调只发一次

**鉴权与隔离**
- `/admin/api/v1` 的 50+ 条路由逐条核对，**全部**挂在 `adminAuth` 之后，仅登录接口故意公开
- 三种 token 靠 `typ` 互斥，用普通 token 调 admin 接口会被拒
- stores / dishes / persona / creations / renders / media / works / account 的主干查询均带 `merchantId`；子资源校验了完整归属链
- STS 临时密钥策略锁死在 `uploads/{merchantId}/*`，`uploads/1/` 不匹配 `uploads/12/`，无法越权写他人目录
- 未发现 mass assignment（zod 默认剥离未知键）；日志未打印 token/密钥/请求体；分页均有上限

**合成链路**
- 命令注入风险不存在：全部 `execFile` 数组参数，文案只作 SRT 文件内容，从不拼进 `-vf`；进 filter 的只有 clamp 后的数字
- 抢锁真原子（单条条件 UPDATE）；`completeRender`/`failRender` 均先 `FOR UPDATE` 再 CAS
- 临时目录在 `finally` 清理；大文件全走流式，没有一次性读入内存
- ChatCut 未知状态一律归 QUEUED，不会把「未知」当成功

**前端**
- token 刷新无竞态（模块级 Promise 保证并发 401 只刷新一次），失败正确清会话跳登录
- 合成提交有 `submitLock` + `pendingTask` 双重拦截；进度轮询有取消、最大失败次数、终态自停

**实现中发现的两个坑（都已处理）**

1. **`grant_expire_at` 是后加字段，现网数据是 NULL。** `merchant 1` 那条 ACTIVE 会员记录的 `grant_expire_at` 就是 NULL——如果只按 `grantExpireAt <= now` 筛选，这条记录永远不进候选，等于**这个 job 上线后对存量会员完全无效**。已改为 `OR` 条件：`grantExpireAt 已过` 或 `grantExpireAt 为空且 endAt 已过`。
2. **续期误清零风险。** `activateMembership` 续期时会把新 `endAt` 写到同一行（`order.service.ts:262-265`），而**旧行会以 ACTIVE + endAt 已过 的形态留下**。若不加判断，一个续了 3 期的用户在旧行到期日会被把赠积分清空。已加两道保护：① 该商户存在 `endAt > now` 的 ACTIVE 会员则跳过；② 该商户存在 `grantExpireAt > now` 的 ACTIVE 会员则跳过。

#### P1-2 `SETTLEMENT_PENDING` 死胡同 —— 已修复并确定性验证

**问题**：`failRender` 里 `unfreeze` 抛错时把任务置为 `SETTLEMENT_PENDING`（前端显示「退款确认中」），但没有任何东西会再动它 —— 原 `sweepStuck` 只扫 `RUNNING/QUEUED`。结果是这笔预留积分**永久冻结**，既不出片也不退钱。

**关键判断：补偿方向只能是 `→ FAILED`（释放），绝不能是 `→ SUCCESS`。**
两边的代价不对称：猜错释放掉一颗积分的损失是「送了一次合成」；猜错结算给用户一个坏文件的损失是「收了钱却没交付 + 用户投诉」。所以补偿只做退款，不做交付。

| 文件 | 改动 |
|---|---|
| `server/src/services/render.service.ts` | 新增 `compensateSettlementPending()` + `sweepSettlementPending()`。上限 `SETTLE_MAX_ATTEMPTS = 5`；宽限期 `SETTLE_GRACE_MS = max(60s, RENDER_SETTLE_GRACE_MS ?? 5min)` |
| `server/src/render/worker.ts` | `sweepStuck()` 末尾追加 `sweepSettlementPending()` 调用与日志 |

**重试节奏的设计（这一步容易做错）**：补偿也失败时，刷新 `finishAt` 作为**宽限锚点**——这样重试间隔恰好等于宽限期，天然形成指数退避。计数用 `retryCount`（schema 里本来就有这一列，之前**零处使用**），但 `failRender` 的 catch 分支里**故意不重置 `retryCount`**：一旦重置，5 次上限永远达不到，会退化成无限重试。这个坑我在实现时先写错了一版，读回才发现的。

#### P2-2 并发同 requestId 提交返回 500 —— 已修复（本条确有其事，且比审读描述更严重）

**审读说**：并发重复请求会返回 500 而非首次结果。

**实测确认**：8 个并发请求打 `POST /creations/:id/render`（同一 `requestId`）→

```
7×  HTTP 500  code=500  提交合成失败
1×  HTTP 200  code=0  ok
```

数据是对的（1 任务 / 1 预留 / 1 条 FREEZE 流水 / frozen 只加一次），**但客户端的 7 个请求全部看到失败**。小程序按 requestId 重试的本意是幂等，实际却会持续吃 5xx 并弹「提交合成失败」。

**根因（用最小复现定位，非推测）**：MySQL 默认隔离级别是 **REPEATABLE READ**。

`claimBusinessRequest` 的流程是「先一致读 → 没有就插入 → 撞唯一索引 P2002 → 再一致读并返回既有行」。问题出在最后一步：

1. 输家事务的第一条一致读（`findUnique`）**就把快照定死了**；
2. 赢家是在输家读完之后才提交的；
3. 于是输家在**同一个事务里**再 `findUnique` **依然返回 null** → 走 `if (!row) throw e` 把 P2002 重新抛出去 → 上层映射成 500。

我把这个假设写成最小事务复现脚本验证，并对比了三种修法：

| 变体 | 做法 | 结果 |
|---|---|---|
| V1 | 现状：先读 → 插入冲突 → 再一致读 | **重读为 null ✗** |
| V2 | 去掉前置读，直接插入冲突 → 再一致读 | 重读命中 ✓ |
| V3 | P2002 后用 `LOCK IN SHARE MODE` 当前读 | 重读命中 ✓ |

**最终修法：给事务显式设置 `isolationLevel: 'ReadCommitted'`**（`render.service.ts::submitRender` 与 `ai/ai.service.ts::runScene`）。

选它而不是逐处塞当前读，是因为「事务内要看见别人刚提交的行」在这个事务里**不止一处** —— 修完 P2002 重读后仍然有 7 个 409：

```
修完 claim 重读后：1×200 + 7×409「已有合成任务进行中」
```

第二处是 `submitRender` 里按 requestId 找 `prior` 任务的 `renderTask.findFirst`，同样是旧快照 → 返回 null → 抛 `RenderAlreadyRunningError`。逐处打补丁容易漏（这已经是第二处），改成 READ COMMITTED 一次覆盖整类问题；`claimBusinessRequest` 里保留了详细注释说明为什么依赖这个隔离级别。

**修复后实测**：

```
8×  HTTP 200  code=0  ok
任务行 1  预留行 1  FREEZE 流水 1  frozen 只加一次
返回的 task.id 990008（8 个响应完全一致）
duplicated 标记 true, true, false, true, true, true, true, true
```

**并回归验证防护没有被削弱**（这是改隔离级别最需要担心的地方）：

| 用例 | 期望 | 实测 |
|---|---|---|
| 5 个**不同** requestId 并发提交同一创作 | 1 成功 + 4×409/4001 | ✓ 通过 |
| 同 requestId 换业务参数 | 409 / code 2007 | ✓ 通过 |

#### P2-10 上传中止 / 孤儿文件 / 轮询无上限 —— 已修复两项，一项如实标注未做

**① `/upload/complete` 失败留孤儿文件 —— 已修复（降低概率）**

原实现：COS/本地上传成功后调用 `/upload/complete`，失败即抛出。对象已在存储里、数据库没有对应行 → 孤儿对象，且**下次重试会生成新的 key**（`Date.now()` 前缀），旧对象永远不会被复用或回收。

> 诚实说明：这降低的是**瞬时网络抖动**造成的孤儿率。真正能兜住「重试也失败」的只有服务端 GC（列举存储对象、比对数据库、清理无主对象），本批**没有做** —— 那属于新增能力而不是 bug 修复，需要单独评估 COS 列举成本和误删风险。

**② 合成轮询无最大时长 —— 已修复**

**③ 上传中止（离开页面继续跑 + 照常落库）—— 已修复**

原实现返回的 Promise 没有任何取消句柄：离开页面后传输继续跑完，然后照常调用 `/upload/complete` —— **用户以为没传成功，数据库里却多了一条素材记录**。

修法分三层：

1. **修正类型声明**（`apps/mini/src/types/cos-wx-sdk-v5.d.ts`）。原声明把 `sliceUploadFile` / `uploadFile` 的返回值标成 `void`，与 SDK 实际行为不符。查源码 `cos-wx-sdk-v5/src/task.js` 确认：`transferToTaskMethod(API_MAP, 'sliceUploadFile')` 把这两个接口改造为**任务式**调用，默认走 `_addTask`、返回 `TaskId`，并通过 `params.onTaskReady(id)` 抛出；取消接口是 `cos.cancelTask(id)`。原声明不仅缺 `onTaskReady`，连返回值都是错的 —— 这也是此前无法实现取消的原因之一。
2. **服务层加 `onTask` / `isCancelled`**（`services/upload.ts`）：本地通道用 `uploadTask.abort()`，COS 通道用 `onTaskReady` 拿 TaskId 后 `cos.cancelTask(taskId)`；各阶段之间检查 `isCancelled()`，命中则抛 `UploadAbortedError`，**不会调用 `/upload/complete`**。
3. **接入分镜上传页**（`pages/creation/shots.tsx`）：页面卸载时统一 abort 所有在途上传，并置 `pageGone` 标志；`catch` 里把 `UploadAbortedError` 与真实失败分开处理（不再对已卸载页面弹「上传失败」）。

**④ 断点续传 —— 未做（如实标注）**

审读提到「无断点续传」。SDK 的 `TaskId` + `pauseTask` 只在**同一次进程内**有意义（`UploadId` 存在内存里）；真正的跨次续传需要持久化 TaskId 与会话参数，并处理上传会话过期，属于新增功能。本批**未实现**，只在类型声明里把 `pauseTask` / `getTaskList` 标出来，方便后续做。

#### 6.5 断点续传：找到了真因，注释写的是错的（P2-10 ④）

原注释说「单文件最大 2GB，**分片续传由 SDK 内部 TaskId 接管**」。**这句话不准确**，读 SDK 源码后确认：

- 真正让续传生效的是 SDK 写在 `wx.setStorageSync('cos_sdk_upload_cache')` 里的 **UploadId 缓存**（`cos-wx-sdk-v5/src/session.js`）。
- 缓存键 = `md5(FilePath)` + `md5(size::mode::lastAccessedTime::lastModifiedTime::ChunkSize::Bucket::**Key**)`，**对象键 Key 也是文件特征值的一部分**。
- 恢复流程：`seek_local_avail_upload_id` → 校验远端 UploadId 仍在 → `multipartListPart` 拉回已上传分片 → **只补传剩余分片**。
- 且 SDK **只在上传成功时清除 UploadId**（`removeUploadId` 仅出现在成功分支），失败后缓存仍在。

**所以问题出在我们自己**：`upload.ts` 每次上传都用 `Date.now()_随机6位` 生成**全新 key** → 缓存键每次都变 → **永远命不中缓存** → 每次失败都从第 0 字节重传，还额外留下一个碎片。

**修复**：新增 `sliceUploadWithRetry`，分片上传失败后**用同一个 key 重试**（退避 `[0, 800, 2000]`），让 SDK 的续传真正生效。取消语义做了双重保护（`cancel.byUser` + `isCancelled`），用户主动取消不重试。

**没有做**的：跨「重新选文件」的续传（`chooseMedia` 每次给新临时路径、mtime 变化，SDK 判定为不同文件），也没有把 key 改成确定性（会让「同一文件传两次」产生**两行共享同一对象**的别名风险，DB 无唯一约束拦不住）。
