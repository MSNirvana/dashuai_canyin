# 配乐曲库（BGM）

这个目录是**运行时数据**，不是源码。渲染时按「风格 → 曲子文件」在这里找曲子。

## 契约：两个位置并存，取用时**池子优先、单文件兜底**

| 位置 | 形态 | 说明 |
| --- | --- | --- |
| **池子** | `LIGHT/` 目录，内含任意多首 | 同风格多条 ⇒ 取用时**轮转派发**（每条片子配乐不重样，见下节） |
| **单文件** | `LIGHT.<ext>` | 老约定，线上现存曲库就是这种，**继续有效** |

- 取用顺序：池子非空就**从池子里派发**；池子为空才回退单文件；
  两头都没有 ⇒ 返回 `null`，调用方回退合成垫底。
- **池子内部的取用是三层**（`worker.ts` 的「配乐取用顺序」注释）：
  ① 按口播内容让模型从候选里挑（`bgm-select.service.ts`）；
  ② 挑不出来 ⇒ 进程内 **LRU 派发器**（`bgm-dispatch.ts`）；
  ③ 池子为空才会走 `resolveBgmTrack()` 的**随机抽取**（= 改动前的行为）。
  ①② 都会再避开「**该门店最近用过的**」曲子（`bgm-history.ts` 读 `RenderTask.bgm_track`）。
- 所以「换生成源」（ChatCut ↔ 火山）**不会覆盖也不会删掉**已有曲子 —— 两个位置互不干涉。
- 扩展名白名单：`mp3 / m4a / aac / wav / flac / ogg / opus`（单文件多扩展名时按此顺序取第一个）。
- 每首曲子旁边的 `.json` 是**旁注元数据**（来源 / 提示词 / 时长 / 授权说明），渲染不读它，
  但 `.json` **不能**被当成曲子取到 —— 两个查找函数都只认音频白名单。
- 目录可由环境变量 `BGM_LIBRARY_DIR` 覆盖；没配就按「模块相对 `../../assets/bgm`」解析，
  所以 `src/` 与 `dist/` 下都能跑。

> ★★ 实现里有个**必须分开**的点：`resolveBgmTrack()` 是「池子优先」，
> 而 `singleFileBgmTrack()` **只看单文件**。补货脚本清理「同风格单文件残留」时必须用后者 ——
> 用前者会在池子非空时删掉**刚攒进池子的曲子**（补一首删一首，池子永远长不大）。
> 守护（`bgm:verify`）为此专门钉了一条断言。

## 两条硬约束

1. **曲子必须不比成片短**（≥ 65s，代码里是 `BGM_MIN_DURATION_MS`）。
   `synthesis.ts::mixAudioTracks()` 用 `amix=duration=longest` 且只输出一条音频流，**不做循环**；
   比成片短的曲子会在中途静音，而且**不报错**。
   ⚠ 不要为了补齐而加 `-stream_loop -1`：混音输出会变成**单条无限流**，`-shortest` 没有有界流可比，
   渲染会**永久挂住**。要循环必须同时给 `-t <成片时长>`，那是另一笔改动。
2. **别手工删这里的东西**。删掉某个风格只是退回合成垫底（不会让出片失败），
   但那正是「配乐像嗡声不像曲子」这个老问题的成因。

## 补货：把池子维持到目标数量

```bash
cd server
npm run bgm:replenish                        # 看现状与计划（不发任何请求）
npm run bgm:replenish -- --yes               # 按缺口补、并把超额部分淘汰（幂等）
npm run bgm:replenish -- --target=8 --max=3  # 目标 8 首/风格，单次每风格最多补 3 首
npm run bgm:replenish -- --prune-only --yes  # 只淘汰超额，不生成
npm run bgm:replenish -- --list              # 只看现状
```

策略三条（每次跑一遍都是幂等的）：池内 **> 目标** ⇒ 淘汰最旧的（连 `.json` 一起清）；
**< 目标** ⇒ 补到目标（单次每风格最多 `--max` 首）；**= 目标** ⇒ 不动。

### 池子能有多大 —— 受提示词表条数限制

`volcano` 源的曲子描述来自 `volcano-bgm.ts::VOLCANO_BGM_PROMPTS`（每个风格一张表）。
补货**只会挑池里没用过的描述**（读侧车 `.json` 的 `prompt` 字段回溯），因此：

- **目标数不要超过表里条数**（现每风格 100 条、池子目标也是 100）。超了就只能复用已有描述 ⇒
  池内一条描述对应好几首 ⇒ **选曲失去区分度**、**曲风单薄**。曲子本身**不会**重复
  （同一段 Text 两次生成结果不同、没有 seed，已实测）。
  守护 `bgm:verify` 把这个关系钉在 `BGM_POOL_TARGET` 上 —— **把目标调大而提示词不够，守护立刻红**。
- 想要更大的池子，**先往表里加词**，再调 `--target`。加词只要满足三条：纯中文（该接口 `Text`
  不支持英文）、写明曲风/乐器/情绪/场景、并显式排除人声（配乐要垫在口播下面）。三条都由守护断言。
- ⚠ 顺序取词有个前提：**池内已有曲子占据了 0..n-1 号描述**。手工单发（`bgm:generate`）是**随机**
  取词的，一旦池子被随机播种过，纯按序号取词就会撞上已经用过的那条描述 ⇒ 所以补货改成了
  「先用没用过的」；`usedBgmPromptTexts` 就是为此存在的。
- **当前目标 = 100 首/风格**（`BGM_POOL_TARGET`，2026-09-28 从 30 提到 100；词表也同步扩到
  每个风格 100 条）。取这个数是为了压「同一门店连续出片至少重样一次」的概率（实测口径：
  同店同风格连续 8 条内至少重样一次 —— N=30 约 64%、N=50 约 45%、N=100 约 **25%**、
  N=125 约 20%）⇒ 100 落在「收益开始迅速衰减」的拐点前。
  ★ **但「同店老听到同几首」不是靠加大池子解决的**：它由「该店用过的曲子全避」那一层负责
  （见下面的派发与去重）。池子大小只影响**短期碰撞概率**。

## 派发与去重：为什么「随机」不够

随机抽取**没有记忆**：同时出片的几条片子两两撞同一首的概率仍是 `1/N`；而用户真正会察觉的是
「**我这个店**连着几条重样」（生日问题，池子再大也躲不掉短期重叠）。

★★ 一个反直觉但很要紧的结论：**`index = f(门店, 时间)` 这类纯函数救不了并发撞车** ——
碰撞概率一样是 `1/N`，而且映射恰好相同的一对门店会**永久**撞在一起（比随机更差）。
要保证两次派发不同，必须有**共享的分配状态**在中间协调。

于是分两层：

| 层 | 文件 | 记忆范围 | 保证 |
| --- | --- | --- | --- |
| 进程内 LRU 派发 | `bgm-dispatch.ts` | 内存，**每个风格一份**，重启即失 | 相邻两次派发**必然**不同首；一个池子被**完整轮转**一遍才回到起点 |
| 门店历史 | `bgm-history.ts` + `RenderTask.bgm_track` | 落库，跨重启、按门店 | 避开该门店**用过的全部**（不截断；候选被占满时放宽） |

- 两层的分工是「**同一时刻别撞**」+「**同一个店别连着重样**」，缺一不可。
- ⚠ **`bgm_track` 列由迁移 `20260928160000_add_render_task_bgm_track` 建**。漏跑迁移不会报错：
  读写都被内部 `catch` 掉 ⇒ **静默退化成「没有历史」**（行为退回纯 LRU 轮转）。
- ⚠ 进程内记忆有个前提：**单进程**。若将来上多实例，这份记忆需要挪到共享存储。
- ⚠ 「不重样」的兜底优先级永远低于「有配乐」：候选被历史占满时会**放宽**（宁可重样），
  这个事实会写进日志（`relaxed`）。

## ★★ 轮换：池子满了之后，怎么继续给用户「没听过的」

池子 100 首**不等于**一家门店有 100 首可听：它听过的那几首会被一直避开（上面那层门店历史），
所以**这家店还能听到的新鲜曲目只会越来越少**。轮换补的就是这一块：
**每天淘汰几首「已经有人听过的」，用新曲子顶上来**（`planBgmRotation` + `removeBgmTracks`）。

```bash
cd /opt/dashuai/server && npx tsx scripts/bgm-replenish.ts --rotate=5           # 看计划（dry-run）
cd /opt/dashuai/server && npx tsx scripts/bgm-replenish.ts --yes --rotate=5     # 真跑
```

- **只淘汰「被派发过」的曲子**（判据来自 `render_task.bgm_track`）。淘汰一首谁都没用过的曲子
  是**纯亏**：没有任何门店因此多听到一首新的；淘汰「听过的」，每一家听过的门店才**净增一首**。
- ★★ **都没有用过 ⇒ 本轮不动**。新池子刚建好时正是这个状态，此时轮换只会平白烧钱。
- **淘汰顺序 = 最久未被派发优先**（不是「用过最多」）：后者会反复换同几首、其它永远轮不到。
- **先删后补，顺序不能反**：补货取词挑的是「池里没用过的描述」，而**删掉侧车 `.json`
  才把那条描述释放回可用池**。★ 所以新曲子会**复用刚腾出来的那几条描述** ⇒ 曲子是新的、
  但**曲风与刚删掉的相近**。要连曲风一起换新，必须**先往 `VOLCANO_BGM_PROMPTS` 加词**。
- **冷却期（默认 6 小时）**：最近这么久内被派发过的**不淘汰**。一次出片是「先记下路径、
  几十秒后 ffmpeg 才去读它」，正好删到那一条 ⇒ `ENOENT` ⇒ **那一单出片失败**。
- **池内没满时不轮换**：轮换是先删后补，补货可能因额度耗尽失败 —— 那就是**净减**。
- `--max` 必须 ≥ `--rotate`（安装器会自动抬）：否则删掉的补不满，池子一天掉一点。
- 成本：`--rotate=5` × 3 风格 × 0.24 元 ≈ **3.6 元/天**；磁盘**不涨**（删 5 补 5）。默认 0 = 关。

## 单风格生成 / 取回

```bash
npm run bgm:generate -- --list                              # 先看现状
npm run bgm:generate -- --style=ALL --yes                   # 补齐缺口（已存在的会跳过）
npm run bgm:generate -- --style=LIGHT --yes --force         # 强制重造某一首
npm run bgm:generate -- --source=volcano --style=LIGHT --yes # 改用火山生成（落池子）
npm run bgm:generate -- --style=UPBEAT --asset=<assetId> --yes --project=<projectId>
                                                            # 只把**已生成好**的素材取回落盘（不再花生成额度）
npm run bgm:verify                                          # 守卫：风格清单同源 / 池子取用 / 火山契约
```

**生成要花钱**（ChatCut 消耗额度；火山按秒计费，约 0.002 元/秒），
所以两个脚本都**默认 dry-run**，必须显式加 `--yes`。

### 两个生成源

| `--source` | 走什么 | 凭证 | 落盘 |
| --- | --- | --- | --- |
| `chatcut`（`bgm:generate` 默认） | ChatCut `submit_music`（mureka-9） | MCP 桥（OAuth） | 默认单文件；加 `--pool` 写池子 |
| `volcano`（`bgm:replenish` 默认） | 火山 `GenBGMForTime`（豆包音乐 v5.0） | `VOLCENGINE_ACCESS_KEY` / `VOLCENGINE_SECRET_KEY`（**AK/SK v4 签名**） | **只写池子** |

> ⚠ 火山的 AK/SK 与火山 **TTS** 的 `X-Api-Key` **不是同一套凭证**，别混。
> 缺凭证时脚本会明确报「缺哪两个变量」且**不会**静默退回另一个源 —— 换源必须是显式的。
> 这两条链路都只在**补货**时联网；渲染管线永远只读本地文件，第三方挂了不影响出片。

### 火山这条源的两个已知约束

- `Text` **仅支持中文**（守护里钉了「纯中文」断言）。
- 公共池 **QPS ≤ 2** 且要排队、单首生成 **1–5 分钟** ⇒ 这正是「不把生成放进出片链路、
  改成后台补货」的原因。补货脚本**顺序**生成，不要并发轰它。

## 当前曲目（服务器上实际内容）

这个目录里**没有版本化的清单** —— 池子是运行时数据、不入 git，数量会随补货变化。
要看**此刻**的现状，用只读命令，别信文档里的数字：

```bash
cd /opt/dashuai/server
npx tsx scripts/bgm-replenish.ts --list       # 各风格池内数量 / 缺口（不发任何请求）
for s in LIGHT UPBEAT PREMIUM; do printf "%-8s %s 首\n" "$s" "$(ls -1 assets/bgm/$s/ 2>/dev/null | grep -Eic '\.(wav|mp3|m4a|aac|flac|ogg|opus)$')"; done
du -sh assets/bgm
```

历史快照（**仅供对照，别当现状**）：最早的曲库是 3 首**单文件** mp3 48kHz 320kbps
（`chatcut:mureka-9`，155~206s，−15.2~−14.0 LUFS）；2026-09-28 起改由火山生成、落**池子**，
每首 120s、16bit/44.1kHz 立体声 WAV ≈ **21 MB**。

> ⚠ 授权以**生成服务当期的服务条款**为准（ChatCut / 火山）—— 商用前请核对并留档。
> 池子铺得越广，这个暴露面越大；`bgm:generate` 会把 `prompt` / 来源写进同名 `.json` 侧车，便于审查。
> 也正因如此，这些音频**不入 git**（仓库是 public，见根目录 `.gitignore` 里的说明）。
