# 支付风控告警 · 运维说明（2026-09-21）

> 这份文档回答一个问题：**支付放开之后，怎么保证「用户付了钱但没拿到东西」不会静默发生。**
>
> 代码位置：`server/src/services/ops-alert.service.ts`（告警出口）、
> `server/src/services/pay-risk.service.ts`（巡检）、
> 守护脚本 `npm run pay-risk:verify`（73 项离线断言）

---

## 一、为什么需要它（缺口有多大）

支付放开之前，「会员」只能由后台手动开通（`adminActivateMembership`），每一笔都有人在场。
`PAYMENTS_ENABLED=true` 之后会员与加油包都走线上收款，而这条链路的失败是**静默**的：

| 环节 | 现状 |
|---|---|
| 微信异步回调 | 不是可靠通道：`notify_url` 不可达 / 网络抖动 / 重试耗尽都会丢 |
| 用户端主动查单 | 只在用户付款后回到页面时触发；用户直接杀掉小程序就没有 |
| 低频对账 sweeper | **只看最近 48 小时**的 PENDING 单 ⇒ 超窗口后**没有任何代码会再看它一眼** |
| 静默分支 | 金额不一致 / 微信侧已退款 / 关单失败 / 查单抛错，原本只有一行 `console.error` |

后果：用户付了 980 元、什么也没得到，而系统里**连一个需要处理的标记都没有**。
（代码里到处写着「没有任何告警」——这次把这句话兑现。）

---

## 二、做了什么

### 1. 一张「事实」表 + 一张「触达」表

| 表 | 性质 | 作用 |
|---|---|---|
| `order_settlement` | 事实 | **结算回执**。与「订单转 PAID」在**同一事务内**写入 ⇒ 存在 ⟺ 事务提交 ⟺ 权益已发 |
| `ops_alert` | 触达 | 所有只能靠人发现的异常的唯一出口。落库 + 可选推送 + 可标记已处理 |

★ 回执为什么不能用权益表反推（两处**必然误报**）：
- MEMBER 续期时 `Membership.sourceOrderId` 仍指向**上一张**订单；
- `grantPoints = 0` 时 `grant()` 根本不会被调用 ⇒「没有流水」既可能是没发、也可能是本就该发 0。

### 2. 一条把「永久静默」变回「有结论」的巡检

`scanStalePendingOrders()` 每小时捞一次 **窗口外**（默认 >48h）+ **有真实微信单**（`wxPrepayId != null`）
+ **本地仍未结清**的订单，逐笔向微信取证并分流：

- `SUCCESS` + 金额一致 → 复用 `markOrderPaid()` 补发权益（幂等）→ 告警 `PAY_RECOVERED_OUTSIDE_WINDOW`
- 未支付且已过期 → 正常关单收尾（**不告警**，这是预期结局）
- **取证抛错 → CRITICAL `PAY_STALE_SETTLE_FAILED`** ← 这就是「扣款成功但开通失败」

> 关键：这批单**不会**再被任何自动流程重试。告警详情里直接附了订单号，
> 让你能去微信商户平台按单号查这笔交易。

### 3. 十个告警类型

| code | 级别 | 含义 / 该怎么办 |
|---|---|---|
| `PAY_STALE_SETTLE_FAILED` | **CRITICAL** | 窗口外取证失败，钱可能收了、货一定没发。**去微信商户平台按订单号查**：收了 → 后台补单；没收 → 确认关单 |
| `PAY_AMOUNT_MISMATCH` | **CRITICAL** | 微信侧金额 ≠ 本地订单金额，已拒绝结算。**不会自愈**（对账走同一条校验，同样拒）。核对是本地金额写错、还是这笔钱不属于这张单 |
| `PAY_PAID_WITHOUT_RECEIPT` | **CRITICAL** | 订单显示已支付却查不到结算回执 ⇒ 有人绕过了 `markOrderPaid()`。逐一核对权益是否真发了 |
| `PAY_REFUND_ANOMALY` | **CRITICAL** | 微信侧已退款但本地从未结算。本项目没有退款入口 ⇒ 账实不符，**系统不自动动账** |
| `PAY_SETTLE_AFTER_TERMINAL` | **CRITICAL** | 订单在 EXPIRED/CANCELLED 下收到支付成功，已按补发处理。核对「本地已关单、微信仍可付」这个窗口怎么出现的 |
| `PAY_RECOVERED_OUTSIDE_WINDOW` | WARN | 窗口外才发现钱已收，已补发。**用户没损失**，但成批出现意味着有用户在静默期一直拿不到权益 |
| `PAY_SETTLED_BY_RECONCILE` | WARN | 回调丢了、由查单补回。单笔正常，**成批出现**请查 `WX_PAY_NOTIFY_URL` 是否可达 |
| `PAY_NOTIFY_FAILED` | WARN | 回调处理失败（已返回 FAIL，微信会重试）。重试耗尽前请人工介入 |
| `PAY_QUERY_FAILED` | WARN | 向微信查单失败。单笔会自动重试；**累计次数持续增长**说明兜底通道整体失效 |
| `PAY_CLOSE_FAILED` | WARN | 微信侧关单失败，订单保持待支付等重试。累计增长说明关单一直失败（查商户私钥/证书） |

★ `occurrences` 这个数字比措辞更能说明严重程度：`PAY_QUERY_FAILED 累计 137 次` ≠ 偶发一次。

## 三、怎么看到告警

### 优先：配一条到手机的通道（强烈建议）

1. 企业微信 → 建一个群（只有自己也行）→ 群设置 → 群机器人 → 添加 → 复制 Webhook 地址
2. 写进服务器 `server/.env`：`OPS_ALERT_WEBHOOK="https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=..."`
3. `pm2 restart dashuai-api --update-env`

判据：启动日志会明确打出

```
[pay-risk] started (... )｜告警渠道：企业微信 webhook 已配置（落库 + 推送）
```

**没配也不会失效** —— 日志会打 `⚠ 未配置 OPS_ALERT_WEBHOOK —— 告警只落库、不会推到手机`，
告警照样进 `ops_alert` 表，从后台看。

### 后台接口

```bash
# 未处理告警（默认 OPEN）+ 未处理总数
curl -H "Authorization: Bearer <admin-token>" \
  'https://admin.dspcz.top/admin/api/v1/ops-alerts?status=OPEN&limit=50'

# 只看资金类
curl -H "Authorization: Bearer <admin-token>" \
  'https://admin.dspcz.top/admin/api/v1/ops-alerts?severity=CRITICAL'

# 标记已处理（处理人与备注会留痕；重复 ack 会被拒，不覆盖首次处理人）
curl -X POST -H "Authorization: Bearer <admin-token>" -H 'content-type: application/json' \
  -d '{"note":"已核对微信侧，确认未收款，已关单"}' \
  'https://admin.dspcz.top/admin/api/v1/ops-alerts/<id>/ack'
```

### 日志

```bash
pm2 logs dashuai-api --lines 500 | grep -E 'ops-alert|pay-risk'
# [ops-alert][CRITICAL] PAY_STALE_SETTLE_FAILED #12 推送成功：窗口外订单取证失败…
# [pay-risk] 巡检：窗口外待核对 2 笔（补单 1 / 收尾 0 / **待人工 1**）｜回执核对 37 笔
```

### 直接查库

```sql
-- 未处理的资金告警
SELECT id, code, severity, title, ref_id, occurrences, last_seen_at, push_status
FROM ops_alert WHERE acked_at IS NULL ORDER BY severity='CRITICAL' DESC, id DESC;

-- 结算回执：某张单到底发了多少
SELECT order_no, order_type, amount_fen, granted_beans, membership_end_at, source, created_at
FROM order_settlement WHERE order_no = 'M...';
```

## 五、守护与排查

```bash
cd /opt/dashuai/server && npm run pay-risk:verify   # 73 项，离线、不联网、不推 webhook
npm run pay-reconcile:verify                        # 55 项（对账链路，含新增的告警断言）
```

**巡检没跑起来**的排查顺序：

1. `resolvePayMode() !== 'real'` ⇒ 日志会打 `[pay-risk] 未启用（支付未开启或为演示模式）`
2. 看 `PAY_RISK_SWEEP_MS` 是否被设成很大的值
3. 启动日志里那行 `[pay-risk] started (...)` 有没有出现

**回执核对报了一堆 `PAY_PAID_WITHOUT_RECEIPT`（几乎一定是假警）**：
说明「回执起点」被算错了。起点**自动取库里最早一条回执的 `createdAt`**；
如果最早那些回执被删过，起点会后移 ⇒ 反而应**漏报**。若真的在报，先查：

```sql
SELECT min(created_at) FROM order_settlement;   -- 起点
SELECT min(paid_at) FROM `order` WHERE status='PAID' AND paid_at IS NOT NULL;
```

两个值接近才正常。需要人工指定时用 `PAY_RISK_RECEIPT_SINCE`。

**告警一直不推送**：看 `ops_alert.push_status` ——
`SKIPPED` = 渠道未配置/限流跳过、`FAILED` = 推送失败（`push_error` 有原因）。
★ 推送失败**不影响落库**，事实不会丢。

## 六、设计上刻意做的取舍（改动前先读）

| 取舍 | 原因 |
|---|---|
| 告警**绝不抛错** | 它跑在支付结算路径上。webhook 超时 / 库抖动 / URL 配错都不允许影响主交易。代价是「告警可能丢」⇒ 所以落库这一层必须存在 |
| 事务内只**收集**、提交后才发 | 不能把 HTTP 往返塞进持有行锁的结算事务里。代价：提交后进程崩溃会丢这条告警，但回执已落库，下次巡检仍能发现 |
| 同键去重 + `occurrences` | 对账每 5 分钟一轮，不去重会把告警群刷到被静音。`occurrences` 保留「持续多久、多少次」 |
| 每分钟推送上限（默认 10） | 企业微信机器人超频会被**停用**。为了多发几条假警而失去唯一触达通道不划算；超限仍落库 |
| 已 ack 的键复发**新开一条** | 问题复发必须重新提醒，不能并进已处理的那条 |
| `ops_alert` **不建外键** | 告警必须能在任何数据状态下写入成功；为已被清理的订单建 FK 会让告警本身写失败 |
| 回执核对**自动推导起点** | 否则第一次上线会把整段历史刷成假警，运营看到一批假警后就再也不会相信它 |
| 窗口外取证**最老的优先** | 它们静默最久、最可能真的收过钱 |
| 无 `wxPrepayId` 的单**不取证** | 微信侧根本没有这张单，不可能收过钱，查它只是浪费外网调用 |
| 只有 ack，**没有删除** | 一条被 ack 的告警就是这笔资金问题的处理记录（`acked_by` / `ack_note`）。删掉等于销毁证据 |
