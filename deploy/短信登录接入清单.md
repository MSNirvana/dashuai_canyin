### ★★ 重要更正（2026-09-16）：签名**没有**被第二次驳回，是在等运营商报备

> ⚠ 本文件上一版写着「第二次改申 `廊坊大帅餐饮管理` 也被驳回」——**这个结论是错的**，
> 来源是把 API 的 `StatusCode = -1` **凭直觉读成了"审核未通过"**。特此更正并保留错误过程。

**真实情况**：控制台的**「报备状态」列显示「报备中」**。

依据（两处一手资料）：

**① SDK 自带类型注释**（`tencentcloud-sdk-nodejs-sms` 的 `sms_models.d.ts::DescribeSignListStatus.StatusCode`）：

```
国内短信 0 表示签名可用，1 表示审核中，2 表示审核通过待生效，
        -1 表示审核未通过、审核失败或【未完成首次报备】等原因导致签名不可用。
国际短信 0 表示审核通过且已生效，1 表示审核中，2 表示审核通过待生效，-1 表示审核未通过或审核失败。
```

⇒ **`-1` 里本来就包含「未完成首次报备」这一支**，不能等同于"被驳回"。

**② 官方《签名实名制报备》的报备状态表**：

| 报备状态 | 含义 |
|---|---|
| **报备中** | **签名已完成腾讯云平台的审核**并已自动向运营商发起实名制报备，尚未收到运营商反馈。部分运营商需 **7-10 个工作日**，运营商未承诺时效，实际可能更长。**报备期间不可编辑签名、不可重新提交报备**（只能撤回报备）。 |
| 报备成功 | 已完成三网至少各一个子端口的报备 |
| 更新报备中 | 历史报备成功过，因端口管控/二次核查被驳回后**再次**报备中 |
| 资料异常 | 资质材料不符合实名规范被驳回（如"一人多企"）⇒ 需更新资料 |
| 报备失败 | 签名内容不合规 / 企业经营状态异常 ⇒ **必须换一个合规签名重新申请** |
| 未报备 | 平台审核通过但未提交报备（申请时没勾该业务场景，或报备需求被撤回） |

⇒ 「报备中」= **腾讯云平台审核已经通过**，正在等运营商。**这是一个好消息，不是坏消息。**

**其余佐证**：

- `ReviewReply` 为空字符串 —— 真被驳回时腾讯云会给理由（第一次「大帅餐饮管理」驳回时就给了
  一大段"偏中性化 / 需带地域名"的具体意见）。**为空恰恰说明不是审核驳回。**
- `QualificationStatusCode = 1`（资质已通过）；模板 `StatusCode = 0`（已生效）。
- 提交时间 `CreateTime = 1789461207` = **2026-09-15 16:33**，到发稿时才 ~18 小时，
  距 7-10 个工作日还早。

**⚠ 把这件事弄错代价很大**：如果按"被驳回"去**重新申请/编辑签名**，
会把正在进行的报备流程**推倒重来**，白等 7-10 个工作日。所以 `sms:status` 已改为
**只陈述"能不能用"、不臆断"为什么不能用"**，并把「等」和「返工」两条路的动作分开写。

**唯一真正需要人做的**：去控制台确认「报备状态」列是 **报备中**（⇒ 等）
而不是 **报备失败 / 资料异常**（⇒ 才需要动）。
<https://console.cloud.tencent.com/smsv2/csms-sign>

## 一、为什么选腾讯云

不是价格因素（各家大厂 0.04~0.05 元/条，差异可忽略），而是**账号收敛**：

- 项目已有腾讯云账号（COS 在用：`COS_SECRET_ID` / `COS_SECRET_KEY`）
- 同账号 ⇒ 同实名主体、同账单、不用再走一遍企业认证
- COS 与短信的控制台、SDK 生态一致，运维心智负担最低

> **建议**：正式接入时给短信单独建一个 **CAM 子账号**，只授予短信权限，而不是直接复用
> `COS_SECRET_ID`。原因：COS 密钥权限很大（可读写/删除全部素材与成片），一旦泄露损失远大于短信；
> 子账号密钥泄露最多被人刷短信用量，可随时禁用。
> 建子账号：<https://console.cloud.tencent.com/cam>
> 嫌麻烦也可以先复用现有密钥跑通，后续再换 —— 代码只需换两个环境变量。

### 步骤 1｜账号实名认证

### 步骤 2｜开通短信服务 + 拿密钥

1. 打开 <https://console.cloud.tencent.com/smsv2>，按提示**开通短信服务**（免费开通，按量/套餐计费）
2. 建 CAM 子账号（建议）：<https://console.cloud.tencent.com/cam> → 新建子用户 →

### 步骤 3｜创建短信应用，拿 SDKAppID

<https://console.cloud.tencent.com/smsv2/app-manage> → **创建应用**（名称随便，如「大帅餐饮小程序」）
→ 得到 **SDKAppID**（形如 `1400123456`）→ 填入 `TENCENT_SMS_SDK_APP_ID`

### 步骤 4｜申请短信签名（**最容易被驳回，重点看**）

<https://console.cloud.tencent.com/smsv2/csms-sign> → 创建签名

- **签名内容**：用**小程序名称**或**公司简称**（主体是「廊坊大帅餐饮管理有限公司」，
  可申请如「大帅餐饮」）。发送时短信里显示为 `【大帅餐饮】您的验证码…`
- **签名类型**：选「**小程序**」最稳妥 —— 与小程序的关联最直接
- **证明材料**：需上传
  - 小程序后台截图（能显示**小程序名称 + AppID**）
  - 主体资质（营业执照）—— 若签名与主体名不一致，需能证明归属关系
- **驳回常见原因**：签名与小程序/主体无明确关联、签名含通用词（如「科技」「服务」）、
  材料截图不含名称

审核一般 **2 小时内 ~ 2 个工作日**。通过后把签名**内容**（不带【】）填入 `TENCENT_SMS_SIGN_NAME`。

### 步骤 5｜申请短信模板

<https://console.cloud.tencent.com/smsv2/csms-template> → 创建正文模板

- **模板类型**：选「**验证码**」
- **推荐模板内容**：

  ```
  您的验证码为{1}，{2}分钟内有效，请勿泄露给他人。
  ```

  `{1}` = 验证码，`{2}` = 有效分钟数（代码里是 **5** 分钟，见 `sms.ts::TTL_MINUTES`）
- **⚠ 变量个数必须与代码传参个数完全一致**，否则运行时直接报
  `FailedOperation.TemplateParamInconsistent`。上面这个模板是 **2 个变量**，
  接入时按 2 个传参（或改用 1 变量模板 `您的验证码为{1}，5分钟内有效。`）
- 通过后得到**模板 ID**（纯数字）→ 填入 `TENCENT_SMS_TEMPLATE_ID`

## 四点六、联调期固定测试码 `123456`（登录后门，仅非 production 生效）

> **动机**：签名还在**运营商报备**（腾讯云平台审核已通过，但报备成功前签名不可用）⇒
> 真实通道发不出短信。本地即便把 `SMS_PROVIDER` 留空，
> 也得先去服务端日志捞明文码（还要额外开 `SMS_LOG_CODE=true`），联调登录页 UI 时很别扭。
> 固定测试码让「手机号 + 验证码」整条链路一步到位地跑通。

### 三道闸门（缺一即关）

`server/src/auth/sms.ts::smsTestCodeConfig(env = process.env)`

| 闸门 | 判据 | 防的是什么 |
|---|---|---|
| ① 环境 | `env.NODE_ENV !== 'production'` | 本地 `.env` 整份复制到服务器；`NODE_ENV` 写错 |
| ② 码形态 | `SMS_TEST_CODE` 必须命中 `/^\d{6}$/` | 手滑写 `SMS_TEST_CODE=true` ⇒ 变成"码值恒为 true" |
| ③ 白名单 | `SMS_TEST_CODE_PHONES` **非空且包含该号** | 一行漏配就全站失守 |

★ **为什么白名单是「必填」而不是「留空 = 所有号」**：
能用一个变量把**任意手机号**变成「输 123456 就能登」，代价是全部商家账号。
要求两个变量同时给对，「**无差别后门**」这件事在本设计里**表达不出来** ——
好的默认值不是"方便"，而是"表达不出危险语义"。

### 接线方式：只替换码值，不豁免流程

```ts
const testCode = smsTestCodeFor(phone)
const code = testCode ?? genCode()                            // ← 只替换码值
await prisma.smsCode.create({ data: { codeHash: hash(code), ... } })
if (testCode) return { cooldownSec: RESEND_COOLDOWN_SEC }      // 不走真实通道
```

★ 这样 `verifyCode()` **一行都不用改** —— 写库时用的就是 `hash(123456)`，于是
「必须有未过期未使用记录 + `attempts < 5` + 哈希相等 + 用后记 `usedAt`」全部照旧生效，
**「必须先点获取验证码」「每号每日 10 条」「IP 每日 50 条」也都保留**。

### 配置（`server/.env`，**不要写进服务器**）

```bash
SMS_TEST_CODE=123456
SMS_TEST_CODE_PHONES=13800000000,13800000001
```

启动时 `app.listen` 回调会 `console.warn` 高亮：
`⚠ 短信测试码已启用（白名单 2 个手机号可用固定验证码登录）—— 这是登录后门，联调结束后请删掉 …`
**只报条数、绝不回显码值**。

`npm run sms:status` 会显示 `测试码 : ⚠ 已启用（6 位，码值不回显）` + **脱敏**白名单。

### 实测（2026-09-16，本机）

```
POST /api/v1/auth/sms/send {"phone":"13800000001"}          → {"code":0,...,"cooldownSec":60}
POST /api/v1/auth/login    {"phone":"13800000001","code":"123456"}
      → {"code":0,...,"merchant":{"id":"3","phone":"13800000001",...}} + token/refreshToken
POST /api/v1/auth/login    {"phone":"13800000001","code":"000000"}
      → {"code":1002,"message":"验证码错误或已过期"}       ← 固定码 ≠ 任意码
```

### ⚠ 两个必须记住的副作用

1. **白名单号在启用期间收不到真实短信** —— 分支在调真实通道之前就 `return` 了。
   签名过审、要把 `SMS_PROVIDER` 切成 `tencent` 验证「真实发送」时，**必须换个不在白名单里的号**，
   否则会看到「接口 200、但没收到短信」而误判成通道有问题（本项目已实测过同类误判）。
2. **用完必须删** —— 联调结束后删掉 `.env` 里的 `SMS_TEST_CODE` / `SMS_TEST_CODE_PHONES`
   两个变量（启动横幅会持续提醒）。真机测试把自己的号加进白名单即可，**但不要放到服务器上**。

## 五、两个必须知道的坑

### 坑 1｜HTTP 请求成功 ≠ 短信发送成功（**会导致静默失败**）

腾讯云 `SendSms` 接口即使**部分/全部号码发送失败，HTTP 也是 200、也不抛异常**，
失败信息在响应体的 `SendStatusSet` 里：

```ts
// 错误写法：没有异常就当成功 → 用户永远收不到短信，系统却认为发成功了
await client.SendSms(req)

// 正确写法：必须逐条检查 Code
const res = await client.SendSms(req)
const st = res.SendStatusSet?.[0]
if (!st || st.Code !== 'Ok') {
  // 发送失败：删除刚写入的 smsCode 记录，再抛错，不能让用户"等一条永远不来的短信"
  await prisma.smsCode.delete({ where: { id: record.id } })
  throw new Error(`短信发送失败：${st?.Code} ${st?.Message}`)
}
```

现有代码在「未配置 provider」时已经采用了「**失败即删除记录**」的正确模式
（`await prisma.smsCode.delete(...)` 后再抛），接真实通道时请沿用同样处理。

### 坑 2｜模板变量个数必须与传参一致

模板 `您的验证码为{1}，{2}分钟内有效。` 有 **2 个变量**，代码就必须传 2 个：

```ts
TemplateParamSet: [code, String(TTL_MINUTES)]
```

少传/多传会报 `FailedOperation.TemplateParamInconsistent`，
且这个错误**同样属于上面的「请求成功但业务失败」**，必须靠 `SendStatusSet` 判断。

另需注意：模板内容与签名都**必须先审核通过**，用未过审的签名/模板发送会报
`FailedOperation.SignatureNotFound` / `FailedOperation.TemplateNotFound`。

## 六、已有的安全与限流（无需新增，但要知晓）

`server/src/auth/sms.ts` 已实现，参数如下：

| 限制 | 值 | 常量 |
|---|---|---|
| 验证码有效期 | 5 分钟 | `TTL_MINUTES` |
| 单条验证码最大尝试次数 | 5 次 | `MAX_ATTEMPTS` |
| 同号重发冷却 | 60 秒 | `RESEND_COOLDOWN_SEC` |
| 单号每日上限 | 10 条 | `DAILY_LIMIT_PER_PHONE` |
| 单 IP 每日上限 | 50 条 | `DAILY_LIMIT_PER_IP` |

其他已有防护：

- 验证码**只存 hash**（`sha256`），不存明文 —— 库被读也拿不到可用验证码
- 校验成功即写 `usedAt`，**不可重放**
- 生产环境（`NODE_ENV=production`）**未配置 provider 时直接拒绝发送**，
  绝不在线上把验证码打到日志
- dev 明文日志**双重开关**（需 `DEV_LOGIN=true` 或 `SMS_LOG_CODE=true`），
  早期只判断「非 production」导致 `NODE_ENV` 写错时线上会泄露验证码，已修

> **⚠ 业务侧提醒**：`loginByPhone()` 走的是 `upsertMerchantByPhone()` —— **手机号没注册过会自动建商户**
> 并触发注册赠积分（`grantRegisterBeanIfNeeded`）。微信一键登录拿的是**微信实名绑定的手机号**，
> 一人一号、切换成本高；短信通道则**允许任何人用任意手机号自助注册**。
> 上面的限流是按号码和 IP 计的，挡得住单点刷量，但挡不住代理 IP 池的批量注册。
> 如果赠积分的价值可观，建议评估是否给「短信注册的新商户」设置不同的初始赠积分策略。
> 现在不一定要处理，但接入前应知晓这个口子的存在。
