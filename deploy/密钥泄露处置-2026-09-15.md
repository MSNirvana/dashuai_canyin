## 4. ★ 为什么不建议清理 git 历史

这是本单最容易被浪费时间的部分，先说结论：**不做**。

| 常见想法 | 现实 |
|---|---|
| 「`git filter-repo` 把历史里的 key 删掉」 | 删完之后密钥**依然是泄露状态** —— 问题不在 git 里，在那把钥匙本身 |
| 「force push 覆盖远端就行了」 | 爬虫、fork、镜像站、CI 缓存、你同事的本地克隆**都留了副本**，改不掉 |
| 「GitHub 上看不到了就算清了」 | GitHub Secret Scanning 及各类第三方密钥库**早已入库**，状态不可回滚 |
| 「至少能减少后续暴露」 | 代价是**所有协作者必须重新克隆**（历史哈希全变），且仓库是个人项目、协作者极少 |

**唯一有效的动作是 §2 的作废重签。**

只有一种情况才值得重写历史：**仓库从未 push 过**（纯本地历史）**且**没有其他协作者。
你现在两个条件都不满足。

## 5. 顺手建议：开启 GitHub 推送保护

public 仓库**免费**，这是唯一能在「已经按下回车」那一刻救命的机制：

`GitHub → 仓库 Settings → Code security → Push protection → Enable`

开启后，含可识别密钥的提交会被 **push 拒绝**，而不是先泄露再补。
（它对自定义格式的 Key 识别有限，所以不能替代 §6 的人工体检，只能兜底。）

本地再加一道 pre-commit 钩子跑 gitleaks 会更稳，需要的话我配上。
