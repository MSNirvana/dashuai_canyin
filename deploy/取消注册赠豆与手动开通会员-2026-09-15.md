## 三、改了哪两件事

### 1. 注册赠豆 `600 → 0`

```bash
# 有 Key 时（脚本要求三个 TB_*_KEY，会连带重配通道，幂等）
TB_GPT_KEY=… TB_CLAUDE_KEY=… TB_DEEPSEEK_KEY=… TB_REGISTER_GRANT=0 npm run ai-channels:setup

# 只改这一个值：用后台【系统配置】页（分组 bean）把 register_grant_points 改成 0
# 或临时脚本 scripts/tmp-set-register-grant.ts（已删）
```

**为什么赠豆也要关**：闸门（`requireSubscription`）与预冻结是**两道门**。
只关闸门而留着 600 赠豆，用户会拿到一堆积分、点生成却被告知「需要订阅」——前后矛盾。
两道门同时关，提示才一致。

**0 值的边界已确认**：

- `auth.service.ts::grantRegisterBeanIfNeeded` 里是 `if (amount > 0n) grant(...)`，
  **0 时跳过发豆但照常置 `registerGrantGranted = true`** ⇒ 不会每次登录重跑事务，也不会留下 0 元流水。
- 不发豆 ⇒ 新用户**不会有 `bean_account` 行**。这是安全的：`lockAccount()` 用 `INSERT IGNORE`、
  `getBalance()` 用 `upsert`，全链路都能自建账户行。
- 把值改回非 0 时，**老用户不会被补发**（`registerGrantGranted` 已置位）——这正是原注释说明的行为。

后台【系统配置】页（`Settings.tsx`，分组默认就是 `bean`）本来就能编辑这些系数，
所以「赠豆多少 / 场景上限多少」随时可改，不用带 Key 跑脚本。

### 2. 后台「手动开通 / 续期会员」

新增 `POST /admin/api/v1/merchants/:id/membership`，入口在
**后台 → 商家详情 → 会员卡片 → 手动开通会员**（可填备注，如「微信转账 980」，会写进赠豆流水）。

**关键设计：不另写一套开会员逻辑。** 它造一张 `amountFen = 0` 的 MEMBER 订单，
然后调用**和微信支付回调完全相同**的 `markOrderPaid()`：

```
后台点按钮
  └─ 建 Order（orderType=MEMBER, amountFen=0, orderNo 前缀 A）
       └─ markOrderPaid(orderNo, wxTransactionId = null)      ← 与支付回调同一个函数
            └─ 终态 CAS：PENDING → PAID（并发/重复点击天然幂等）
                 └─ activateMembership()
                      ├─ 有有效会员 ⇒ 在现有 endAt 上顺延 30 天
                      └─ grant(source='MEMBERSHIP') → 进**会员桶**，随会员到期清零
```

这样做的收益，都是「另写一套」会踩的坑：

| 如果另写一套 | 走同一个 `markOrderPaid` |
|---|---|
| 容易把赠豆发进 GRANT/充值桶，到期不清零、还能提现式滥用 | 会员桶，口径与线上购买一致 |
| 续期容易变成「覆盖」而不是「顺延」 | 复用 `activateMembership` 的顺延分支 |
| 幂等键 `membership:<orderId>` 可能重复 ⇒ 重复发豆 | 每次开通一张新订单，键天然唯一 |
| 后台查不到「谁发的」 | 留下订单行（`orderNo` 前缀 `A`）+ 赠豆流水备注含操作人 `admin#<id>` |

## 四、账务口径（已验收）

| 项 | 值 |
|---|---|
| 会员桶 | `bean_account.grant_balance` —— 随会员到期**清零**（`grant-expiry` 调度 → `expireGrant`） |
| 注册桶 | `bean_account.grant_register_balance` —— **永久有效**，不参与到期清零（现在是 0） |
| 幂等键 | 赠豆流水 `request_id = membership:<orderId>`，唯一索引 `(merchantId,bizType,requestId,type)` |
| 单号前缀 | `B` = 线上充值、`M` = 线上买会员、**`A` = 后台手动开通** |
| 订单金额 | `amount_fen = 0`、`original_amount_fen = 98000`（后者留档「本应值多少」） |
| 微信交易号 | `null`（未经过支付）—— `order.wx_transaction_id` 可空且唯一，不冲突 |
| 续期 | 已有有效会员 ⇒ `newEnd = existing.endAt + 30 天`；否则 `now + 30 天` |

> **操作不可撤销**：后台每点一次就是一次真实开通 + 发 98000 积分。
> 前端已加 `confirmDialog` 二次确认，并在弹窗里预告「到期时间 + 送多少积分」。

## 六、为什么没有顺手打开支付

`resolvePayMode()` 在服务器上是 `'disabled'`（`PAYMENTS_ENABLED=false` + `NODE_ENV=production`），
下单会返回 **3008「支付功能暂未开放」**。不打开它是因为：

1. **备案未过** ⇒ 微信支付回调按 Host 被腾讯云接入层拦掉 ⇒ 用户**付了钱拿不到会员**；
2. **没有对账 / 补单机制**：会员权益**只由** `handleNotify` 发放，没有主动查单、没有 cron。
   一旦回调丢了，只能人工发现、人工补。

所以顺序是：**备案通过 → `PAYMENTS_ENABLED=true` → 重启**，在那之前一律走后台手动开通。
