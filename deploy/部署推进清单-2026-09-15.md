### 证据（实测）

腾讯云备案拦截页自己会查一个状态接口，直接调它得到：

```
POST https://dnspod.qcloud.com/cgi/capi?action=DescribeDomainIcpStatus
     {"Domain": "dspcz.top"}

→ {"GovStatus": false, "LandedStatus": false, "AuditTicket": false, "Ban": false}
```

| 字段 | 含义 | 实测值 |
|---|---|---|
| `GovStatus` | 工信部备案是否完成 | **false** |
| `LandedStatus` | 是否已接入腾讯云 | **false** |
| `AuditTicket` | 是否有审核中的申请 | **false** |
| `Ban` | 是否被封禁 | false |

> **⚠ 这行判读是错的，别信它（保留作反面教材）。**
> 我当时看到三个 `false` 就推断「没有审核中的单子 → 备案还没提交」。
> **错。** 这个接口查的是「**腾讯云这一侧的记录**」：
> `AuditTicket=false` 只表示「腾讯云侧没有审核中的单子」，
> 而**接入备案的审核发生在管局、不在腾讯云侧**，所以接入备案期间这里照样是 `false`。
> 同理 `LandedStatus=false` 正是「还没接入腾讯云」的**正常中间态**，不是「从未备案」。
>
> **教训：接口的三个 `false` 只说明「本厂商侧暂无有效记录」，
> 推不出「用户没做过备案」。** 要判断真实状态，必须看云厂商备案控制台或问用户拿订单号。

### 表现

```bash
$ curl -i http://api.dspcz.top/healthz
HTTP/1.1 302 OK
Location: https://dnspod.qcloud.com/static/webblock.html?d=api.dspcz.top

$ curl -i http://dspcz.top/
HTTP/1.1 302 OK
Location: https://dnspod.qcloud.com/static/webblock.html?d=dspcz.top

# 连直连 IP + Host 头也一样被拦（说明拦在腾讯云接入层，不经过我们的 nginx）
$ curl -H 'Host: api.dspcz.top' http://49.232.243.241/healthz
HTTP/1.1 302  → webblock.html?d=api.dspcz.top
```

拦截页正文写着「**网站暂时无法访问**」「去腾讯云备案控制台」，CSS 类是 `beian-block-container`。

**域名解析本身完全正常**（四个解析器都返回 49.232.243.241），所以问题不在 DNS，
而在腾讯云的接入网关：**凡「本厂商侧尚无已完成备案记录」的域名，HTTP 请求一律被替换成拦截页**
（接入备案在管局通过前正属于这一状态，见下方说明）。

**HTTPS 同样被拦，但机制不同（2026-09-15 11:10 实测）**：在服务器上起了个自签证书的
HTTPS 临时服务，做了两组对照 ——

| 请求 | 结果 | 含义 |
|---|---|---|
| `curl -k https://api.dspcz.top/` | `(35) Recv failure: Connection reset by peer` | **按 SNI 识别域名后直接 RST** |
| `curl -k -H 'Host: api.dspcz.top' https://49.232.243.241/` | `ORIGIN-REACHED: this response comes from OUR server…` | 无 SNI 就到达了源站 |

**推论：DNS-01 签证书绕不过备案。** 证书能签出来，但小程序/浏览器握手时 SNI 一出现就被重置。
HTTP-01 和 DNS-01 两条路都堵死，**只有「备案完成」或「换已备案域名」两个选择**。

> 附带纠正一个我先前的误判：443 **其实早就放行了**。我用 `nc -z` 探测，
> 但 `nc -z` 要求「防火墙放行」**且**「有服务监听」同时成立 —— 当时 nginx 只监听 80，
> 443 上没有任何服务，所以必然失败，被我错读成「防火墙没放行」。
> 用临时监听法复测：本地三次 TCP 全部建立成功，服务器端也收到了
> `GOTCONN from ('183.250.114.46', …)` 三次 —— 防火墙确实是通的。

### 三个后果

1. **HTTPS 证书签不了** —— Let's Encrypt 的 HTTP-01 校验访问
   `http://api.dspcz.top/.well-known/acme-challenge/...`，拿到的是拦截页而不是校验文件。
   实测报错：
   ```
   Detail: 43.174.225.201: Invalid response from
           https://dnspod.qcloud.com/static/webblock.html?d=api.dspcz.top
   ```
2. **小程序用不了** —— 微信要求「服务器域名」必须已备案，且真机请求必须能通。
   体验版一样受这个限制（体验版不豁免合法域名校验）。
3. **后台用不了** —— `admin.dspcz.top` 同样被拦。

### ★ 审核期间被拦是**预期行为**，不用怀疑自己的配置

这点必须说清楚，否则很容易在等待期间反复折腾服务器：

**腾讯云的拦截判定依据是「本厂商侧是否有已完成的备案记录」。**
接入备案在管局通过之前，腾讯云侧始终没有这条记录 —— 所以**从你提交申请到管局通过的全过程，
域名一直会被拦**。这不是配置错了，也不是服务器没跑起来，更不是安全组的问题。
服务器侧我们已经逐项实测通过（第 2 节），**任何在服务器上的改动都改变不了这个拦截**。

同理，这段时间**不要再做以下尝试**，它们全部无效：

| 尝试 | 为什么无效 |
|---|---|
| 换证书 / 自签证书 | 拦截发生在 TLS 握手之前按 SNI 判定，证书根本没机会被看到 |
| DNS-01 方式签 Let's Encrypt 证书 | 证书能签出来，但小程序握手时 SNI 一出现就被 RST |
| 检查/放开安全组、防火墙 | 请求压根没到服务器，安全组放不放行都无关 |
| 换绑 IP、改 nginx 配置 | 拦截在腾讯云接入层，在源站之前 |
| 直连 IP 测试 | 直连 IP（无 SNI、无域名）**能通**，但那不代表域名可用 |

> 唯一需要盯的：备案状态变更一般会有短信/站内信通知，**通过后域名会在很短时间内自动放行**
> （通常几分钟到几小时，不用再提交任何操作）。

## 3. 本轮修掉的三个 bug

### 3.1 `deploy.sh` 第 7 步：PM2 配置路径（**阻断部署**）

第 4 步执行过 `cd "$SERVER_DIR"`，之后 cwd 一直停在 `server/`，
第 7 步却写相对路径 `pm2 startOrReload deploy/ecosystem.config.cjs`，
被解析成 `server/deploy/...` → `[PM2][ERROR] File deploy/ecosystem.config.cjs not found`。
已改为绝对路径 `$APP_DIR/deploy/ecosystem.config.cjs`，并给 `/var/log/dashuai` 加了 sudo fallback。

### 3.2 compose 端口覆盖语义（**阻断部署**）

`docker-compose.override.yml` 里直接写 `ports: ["127.0.0.1:6379:6379"]` 是错的 ——
compose 对 `ports` 是**列表追加**，会与主文件的 `6379:6379` 叠加成两条冲突映射：

```
failed to bind host port 127.0.0.1:6379/tcp: address already in use
```

必须用 `!override` 标签整段替换。`environment` 是 map 语义，同名 key 直接覆盖，无需 `!override`。

### 3.3 `deploy.sh` 的 libass 误报（**误导运维，不阻断**）

用 `ffmpeg -filters | grep -q ' subtitles '` 判断 libass：`grep -q` 一匹配就关闭管道，
ffmpeg 收到 SIGPIPE 异常终止（exit 141），在 `set -o pipefail` 下整条管道被判为失败 →
**明明有滤镜也报「缺 libass」**。已改成先收变量再 `case` 匹配，并补上中文字体检查。

### 3.4 修复后已完整重跑验证

三个 bug 全修完之后重跑了一次 `bash deploy/deploy.sh`，七个步骤全程无阻：

```
==> [1/7] 检查运行环境
    libass: 可用（支持字幕烧录）            ← 旧逻辑在此处会误报「缺 libass」
    CJK字体: 可用（/usr/share/fonts/opentype/noto）
==> [3/7] Container dashuai-mysql  Started   ← 旧 override 在此处会报 address already in use
==> [7/7] 启动 PM2 进程                      ← 旧写法在此处会报 File not found
==> 健康检查
    http://127.0.0.1:3000/healthz  OK
```

## 6. AI 通道：seed 已经把它关掉了

seed 输出明确写着：

```
[seed] 未找到已启用的真实模型，AI 场景回退到 MOCK 通道（本地联调）
```

因为 `prisma/seed.ts` 在**创建和更新两条路径都把 `enabled` 写成 `false`**，
而 `MOCK_AI=false` 在 production 下强制 —— 所以现在小程序里点 AI 生成会失败。

顺序必须是：

1. `.env` 填 `DEEPSEEK_API_KEY`
2. `npm run db:seed`
3. 登录后台 →「供应商配置」(`apps/admin/src/pages/AiProviders.tsx`) **手动启用 DeepSeek**
4. 场景的 `defaultModelId` 才会绑到真实通道
