## 1. 硬阻断（不做这两件，后面全部走不通）

### ① 补 `api.dspcz.top` 的 A 记录

你给的域名 DNS 我实测了一遍：

| 域名 | 当前解析 | 结论 |
|---|---|---|
| `dspcz.top` | → 49.232.243.241 | ✅ |
| `www.dspcz.top` | → 49.232.243.241 | ✅（未使用） |
| `admin.dspcz.top` | → 49.232.243.241 | ✅ 后台用 |
| `api.dspcz.top` | **无记录** | ❌ **必须补** |

到「腾讯云 → DNSPod → 解析」加一条：

```
主机记录：api
记录类型：A
记录值：  49.232.243.241
```

**为什么不能省**：小程序所有请求走 `https://api.dspcz.top/api/v1`；
`deploy/nginx/dashuai-api.conf` 的 `server_name`、`.env` 的 `CORS_ORIGIN` 与
`WX_PAY_NOTIFY_URL`、小程序出包的地址都指向它；certbot 也要能解析到它才能签证书。

### ② 安全组放行 80 / 443

实测从外网探测：**22 通，80 / 443 全部 filtered**。
不放行的话 nginx 起得来但外网访问不到，`certbot --nginx` 的 http-01 校验也必然失败。

到「控制台 → 服务器 → 防火墙（安全组）」放行 TCP **80** 和 **443**。

> 顺带：3306 / 6379 目前也是 filtered。这是好事 —— 仓库里 `docker-compose.yml`
> 把这两个端口映到了 `0.0.0.0`，靠的就是安全组挡住。我已用 override 文件把它们改成
> 只绑 `127.0.0.1`，所以**不要**为了图方便去放行这两个端口。

踩到并已修掉的四个坑（照官方文档会卡住）：

1. **不需要 NodeSource** —— Ubuntu 26.04 代号 `resolute`，未必有源；apt 自带的 22.22.1 够用
2. **必须另装中文字体** —— apt 的 ffmpeg 有 libass，但系统 0 个 CJK 字体；
   `synthesis.ts` 找不到字体就**静默降级为仅配音、不烧字幕**
3. **Docker Hub 直连超时** —— 已配 `registry-mirrors = mirror.ccs.tencentyun.com`（0.03s）
4. **预置 `~/.npmrc` 是坏的** —— 指向的 `mirrors.tencentyun.com/npm` 返回 404，已改成 `registry.npmmirror.com`

**字幕烧录已实测通过**：中文 SRT + `Noto Sans CJK SC` + fontsdir 跑通，
抽帧对比 1504 → 7475 bytes，像素确实烧进了画面。

另外修掉了 `deploy/deploy.sh` 一个会误导运维的 bug：它用
`ffmpeg -filters | grep -q ' subtitles '` 判断 libass，而 `grep -q` 一匹配就关闭管道，
ffmpeg 收到 SIGPIPE 异常终止（exit 141），在 `set -o pipefail` 下**明明有滤镜也报「缺 libass」**。
已改成先收变量再 `case` 匹配。

## 6. 剩下我可以直接做的（等 ①②⑤ 和 push 就位）

按这个顺序，全部由我执行：

1. 服务器 `git clone` 到 `/opt/dashuai`，放好 `.env` 与 compose override
2. `bash deploy/deploy.sh` —— 起 MySQL/Redis → 装依赖 → 编译 → 建表 → seed → PM2 启动 → 健康检查
3. nginx 两站点配置 + `certbot` 签 HTTPS 证书
4. `apps/admin` 构建（**注意 `deploy.sh` 不构建后台前端**，而 nginx 的 root 指向
   `apps/admin/dist`，不构建会 403）
5. **AI 通道启用**（这一步容易漏，见下）
6. 本地小程序出包：`bash scripts/build-weapp-prod.sh https://api.dspcz.top/api/v1`
7. 真机验收（`deploy/README.md` 第 6 节有 13 条清单）

### 关于第 5 步：AI 上线的隐藏链路

`DEEPSEEK_API_KEY` **在 `server/src/` 里完全没被引用**，只被 `prisma/seed.ts` 用：
seed 把 key 用 `APP_MASTER_KEY` 加密后写进 `ai_provider` 表，并且
**创建和更新两条路径都把 `enabled` 写成 `false`** —— 每次 seed 都会把它关回去。

所以 AI 真实可用的顺序是：

1. `.env` 填 `DEEPSEEK_API_KEY`
2. `npm run db:seed`
3. 登录 `admin.dspcz.top` →「供应商配置」**手动启用 DeepSeek**
4. 场景的 `defaultModelId` 才会绑到真实通道（seed 的策略是「优先绑已启用的真实模型，
   否则退回 MOCK」，而 `MOCK_AI=false` 在 production 下强制 —— 绑错了 AI 调用就失败）
