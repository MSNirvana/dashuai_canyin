另加：

| 变量 | 值 | 说明 |
|---|---|---|
| `PAYMENTS_ENABLED` | `true`（或删掉这行） | 现在服务器上是 `false`，**必须改**，否则下单被拒（业务码 3008） |
| `PAYMENT_MODE` | `real` | 生产下 `paymentsEnabled=true` 时**强制**要求 `real`，不写会拒绝启动 |

> **格式陷阱（第 4、7 项）**：这两个是多行 PEM，但 `.env` 里必须写成**单行**，
> 换行用字面 `\n` 表示 —— 代码里执行 `replace(/\\n/g, '\n')` 还原。
> 直接把 PEM 原样粘进 `.env` 会解析失败。

生成单行值：

```bash
awk 'NF {sub(/\r/, ""); printf "%s\\n", $0}' apiclient_key.pem
```

## 三、商户平台侧还要做的（非代码，缺一个都付不了钱）

这几件事不在 `.env` 里，但**不做就报错**：

1. **开户成功** —— 注册 ≠ 可用。必须走完 提交资料 → 审核 → **账户验证**（法人扫脸或小额打款）

2. **关联 AppID（关键）** —— 「产品中心 → **AppID账号管理**」把小程序 `wx3004f53da3e30a36`

4. **绑定结算银行卡** —— 「账户中心 → 结算账户」，否则收不了款。
5. **确认 `notify_url` 公网可达** —— 见下节。

## 五、⚠ 需要你确认的一个技术分叉

### ✅ 已确认（2026-09-15）：本商户是「微信支付公钥」模式

原先代码只接受平台证书：`platformCert.includes('BEGIN CERTIFICATE')`。
实测发现本商户走的是**公钥模式**，该条件永远为假 → `wxpayEnabled` 静默变成 `false`
（服务器照常启动、下单全被拒、回调验签全失败）。**已修复**，两种模式现在都支持。

**怎么发现的**：用商户 API 证书签名调 `GET /v3/certificates`，返回

```
404 RESOURCE_NOT_EXISTS
无可用的平台证书，请在商户平台-API安全申请使用微信支付公钥。
```

> 附带两个副产品：
> 1. 这个 404 而**不是** `SIGN_ERROR`，说明**商户 API 证书签名是成功的** ——
>    商户号 / 序列号 / 私钥三者配套无误。
> 2. Node 的 `fetch`/undici 默认**不发 `Accept-Language`**，而微信支付 v3 会因此返回
>    一个极具误导性的 `406 PARAM_ERROR 传入了不支持的Accept-Language`。
>    排查时请**显式带上** `Accept-Language: zh-CN`，否则会顺着假错误白找半天。

### 两种模式的关系（务必分清，很容易搞混）

| | 商户 API 证书 | 微信支付平台证书 / 微信支付公钥 |
|---|---|---|
| 代表身份 | **商户侧** | **微信侧** |
| 用途 | 我们对微信**请求**的**签名** | 验证微信**下发**的回调与响应**签名** |
| 环境变量 | `WX_PAY_PRIVATE_KEY` + `WX_PAY_SERIAL_NO` | `WX_PAY_PLATFORM_CERT` |
| 来源 | API安全 → 申请API证书（zip） | API安全 → 微信支付公钥管理 / 平台证书 |
| 有效期 | 5 年 | 平台证书 5 年（需轮换）；**公钥不过期** |

平台证书与微信支付公钥**二选一**，功能完全等价 —— 微信 2024 年底推出公钥是为了
免去「证书会过期、要定期调接口轮换」的运维负担，因此**新商户默认只有公钥**。

### 代码侧改动

- `src/lib/wxpay.ts`：`wxpayEnabled` 改为接受两种形态（新增 `wechatVerifyMode()` 判断）；
  `verifyNotify()` 无需分叉 —— `crypto.verify()` 对 X.509 证书 PEM 和 SPKI 公钥 PEM 都支持。
  另为可测试性给 `verifyNotify()` / `wechatVerifyMode()` 加了可注入的凭据参数。
- `src/lib/config.ts`：生产校验加了一句 —— 验签凭据必须含 `BEGIN CERTIFICATE` 或
  `BEGIN PUBLIC KEY`，否则直接拒绝启动。原先只查非空，填错内容会**静默**降级。
- 契约测试：`npm run wxpay:verify`（`scripts/verify-wxpay-notify-signature.ts`），
  23 条断言覆盖两种模式的验签矩阵（篡改 / 伪造 / 过期 / 缺头 / 空材料全部拒绝）
  + 子进程验证真实 `wxpayEnabled` 常量在公钥模式下为 `true`。

> `Wechatpay-Serial` 头**刻意不强制校验**：本商户只配一把微信侧钥匙，没有歧义；
> 只要签名能过就是微信发的。而微信在「证书 → 公钥」灰度期该头可能仍返回平台证书序列号，
> 强校验会把合法回调误判为伪造 —— 那才是真事故（用户付了钱拿不到积分）。
> 代码里改为**只记录不拒绝**（`describeNotifySerial()`，`routes/pay.ts` 会打印）。

### 公钥 ID ≠ 公钥文件（别混）

| | 公钥 ID | 公钥文件（`wxp_pub.pem`） |
|---|---|---|
| 形态 | `PUB_KEY_ID_0117504054172026091500191587002400` | `-----BEGIN PUBLIC KEY-----...` |
| 是什么 | 一把钥匙的**名字/编号** | **密钥材料本身** |
| 能否用于验签 | ❌ **不能** | ✅ 能 |
| 用途 | 微信在 `Wechatpay-Serial` 头里指明用哪把钥匙；商户上送**加密敏感信息**时也要带这个头 | 实际参与 RSA 验签 / 加密 |

**本项目的 JSAPI 下单 + 回调不涉及上送加密敏感信息，所以公钥 ID 不是必需项** ——
配置它只是为了在日志里核对回调头，便于真机排查。

**实测（2026-09-15）**：调两个 v3 接口，微信响应头均返回
`wechatpay-serial = PUB_KEY_ID_0117504054172026091500191587002400`，与商户平台一致
（该 ID 串中还嵌着商户号 `1750405417`，可交叉确认归属）。已写入 `WX_PAY_PUBLIC_KEY_ID`。

### 新增：`npm run wxpay:probe` —— 收款前就能确认「接入是否成功」

`server/scripts/probe-wxpay-live.ts`，**只读**（只发 GET，不建单、不退款、不动钱）：

```bash

```

它做四件事，把「凭据到底在微信那边有没有效」这件事变成一条命令：

| 步骤 | 内容 | 期望 |
|---|---|---|
| 一 | 七项凭据齐备性（含 APIv3 密钥**正好 32 字符**、序列号 40 位十六进制、验签材料形态） | 全 ✓ |

## 八、安全提醒

- **`WX_PAY_PRIVATE_KEY` 和 `WX_PAY_API_KEY_V3` 是能签发支付请求的凭据**，
  泄露等于别人可以用你的商户号下单/退款。只放在服务器 `.env`（600）与
  `~/.dashuai-deploy/`（仓库外，不进 git）。
- APIv3 密钥商户平台只显示一次；私钥只能生成一次。**先各自存一份到密码管理器再继续。**
- 商户证书与公钥文件在 `~/.dashuai-deploy/wxpay/`（目录 700、文件 600）：
  `apiclient_cert.pem` / `apiclient_key.pem` / `apiclient_cert.p12` /
  `wxpay_pub_key.pem` / `README_CN.txt`。

## 九、回调丢了 = 钱付了没权益（✅ 2026-09-15 已实现三通道兜底）

**设计前提**：会员/积分**只由** `order.service.ts::markOrderPaid()` 发放 ——
`routes/pay.ts` 收回调 → `markOrderPaid()` → 发豆 / 开会员。
所以修法不必新造账务逻辑，只要让**别的路径也能抵达同一个 `markOrderPaid()`**。

### 风险与已经踩过的事实

| 场景 | 后果 |
|---|---|
| 回调网络抖动 / 超时 | 用户付了钱，**权益没发**，且系统里看不到异常（订单停在 PENDING，慢慢过期） |
| 备案未过（当前） | 回调**100% 到不了**（域名被接入层 302 拦掉）⇒ 现在就等于「一付款就丢单」 |
| 微信重试 8 次后放弃 | 同上，且不会再有自动补偿 |

### 已实现：三条通道，全部复用 `markOrderPaid()`

核心是 `server/src/services/pay-reconcile.service.ts::queryAndSettle()`，它**只做一件事**：
调微信查单接口拿真实状态，若 `SUCCESS` 就调**同一个** `markOrderPaid()` 补发权益。

| # | 通道 | 入口 | 触发时机 |
|---|---|---|---|
| ① | **用户端主动查单** | `POST /api/v1/orders/:orderNo/query` | 小程序付款返回后立即轮询（最多 6 次 / 间隔 2s） |
| ② | **低频对账 sweeper** | `src/index.ts` 启动时按既有 worker 模式注册 | 每 `PAY_RECONCILE_SWEEP_MS`（默认 5 分钟）扫最近 `PAY_RECONCILE_WINDOW_HOURS`（默认 48h）的 PENDING 单，每轮 50 笔 |
| ③ | **后台人工补单** | `POST /admin/api/v1/orders/:orderNo/reconcile` ＋ 后台「商家详情 → 最近订单」的「补单」按钮 | 前两者都失效时人工点 |

> 为什么前端不能只继续轮询 `GET /orders/{orderNo}`：那只读**本地库**，
> 回调丢了这个单会**永远停在 PENDING**，用户看到的就是「钱付了、积分不到账」。
> 所以改成了**主动向微信查单**。

### 为什么不可能重复发权益

三条通道最终都落到 `markOrderPaid()`，而它是**终态 CAS**：

```ts
updateMany({ where: { orderNo, status: 'PENDING' }, data: { status: 'PAID', ... } })
// claimed.count === 0 ⇒ 直接 return，不再发任何权益
```

所以「用户连点 / 对账与回调同时到达 / 后台重复点补单」都只会发一次。
关单同理：`closeLocal()` 也是 `where: { status: 'PENDING' }` 条件更新，
**绝不会覆盖 PAID** —— 对账扫到一笔已被结算的单，不会被误改成 EXPIRED/CANCELLED。

### 三条安全约束（都有断言锁住）

1. **金额必须一致**：微信侧 `amount.total` ≠ 本地 `order.amountFen` 时**拒绝自动结算**、
   一分不发，只打 `[pay-reconcile] 金额不一致，拒绝结算` 日志交人工（防「改金额白拿权益」）。
2. **查单响应必须验签 + fail-closed**：查单结果会直接发权益，属**可信输入** ⇒
   验签不通过宁可抛错让上层重试（用户端返 5xx、前端继续轮询），**绝不据此结算**。
3. **越权防护**：用户端接口强制带 `merchantId`，拿别人的订单号查只会得到 404。

### 不查的单（避免无意义的外网请求）

`A` 前缀（后台线下单，微信侧根本不存在）／支付非 `real` 模式（demo / disabled）／已终态的单
—— 全部直接 `SKIPPED`。sweeper 在 `resolvePayMode() !== 'real'`（即 `PAYMENTS_ENABLED=false`）时
**根本不启动**，日志干净。

### 各 `trade_state` 的处理

| 微信返回 | 本地动作 |
|---|---|
| `SUCCESS` | 校验金额一致 → `markOrderPaid()` ⇒ PAID |
| `NOTPAY` / `USERPAYING` | 已过期 → EXPIRED；否则保持 PENDING（用户可能正在输密码） |
| `CLOSED` / `REVOKED` / `PAYERROR` | 已过期 → EXPIRED；否则 CANCELLED |
| `REFUND` | **不自动动账**，只交人工（退款流程另有设计） |
| `NOT_EXIST`（404） | 已过期才关单，未过期不动（可能只是刚下单、微信侧还没落库） |

### 验证

```bash
npm run pay-reconcile:verify     # 40 断言 / 0 失败（完全离线：查单函数注入，不碰真凭据、不发外网请求）
npm run wxpay:verify             # 34 断言 / 0 失败（新增 E 段锁住 verifyResponse 的 Headers 路径与 fail-closed）
```

`pay-reconcile:verify` 九节覆盖：已 PAID 不查微信 / 金额一致才结算且重复不双发 /
金额不一致拒绝 / 未支付的两种分支 / `CLOSED` / `NOT_EXIST` / 不该查的单全 SKIPPED /
越权 / sweeper 只补窗口内且第二轮不重复发。跑在一次性手机号商户上，跑完硬删。

### 遗留

- **撤销/退款入口仍缺**：对账遇到 `REFUND` 只能提示人工，没有 UI 可发起退款。
- **对账窗口 48h**：超过 48h 的悬空单不再自动扫，需人工用通道③补。
- **通道③是「重新查单」而不是「强制置为已支付」**：仍以微信侧真实状态为准，
  不能凭空把未付款的单改成已支付 —— 这是刻意的（否则就成了一个可被滥用的白拿入口）。
