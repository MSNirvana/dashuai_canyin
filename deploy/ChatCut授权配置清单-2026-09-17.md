## 一、一句话结论

**ChatCut 的授权是标准 OAuth 2.0，而且「点同意」这一步必须由人在浏览器里完成** ——
我们的服务端是无头后端，没有浏览器，所以它**永远不可能自己完成这一步**。

> 这就是「AI 档为什么接不上」的根本原因：不是代码半成品，也不是网络不通
> （实测端点可达，HTTP 401 / 1.07s），而是**这一步从来没有人在 ChatCut 侧做过**。

顺带一条容易踩反的认知：授权完成后要拿的是 **refresh_token**（不是 access token）。
只填 access token 的话，它一过期（通常 1 小时）通道就静默失效，且**不会有任何告警**。

## 二、实测到的 ChatCut 授权端点

未授权请求会返回这样的响应头：

```
HTTP/2 401
www-authenticate: Bearer resource_metadata="https://api.chatcut.io/.well-known/oauth-protected-resource/api/external-mcp/mcp"

{"error":{"code":-32000,"message":"Unauthorized: Authorization: Bearer <chatcut API key or JWT> is required"}}
```

顺着这个头把元数据拉下来（RFC 9728 → RFC 8414），全部端点如下 —— **下面是现场拉取的结果，不是抄文档**：

| 项 | 值 |
|---|---|
| resource | `https://api.chatcut.io/api/external-mcp/mcp` |
| authorization_server | `https://api.chatcut.io` |
| authorization_endpoint | `https://api.chatcut.io/auth/mcp/authorize` |
| token_endpoint | `https://api.chatcut.io/auth/mcp/token` |
| **registration_endpoint** | `https://api.chatcut.io/auth/mcp/register` ← **支持动态客户端注册** |
| userinfo_endpoint | `https://api.chatcut.io/auth/mcp/userinfo` |
| grant_types_supported | `authorization_code`, `refresh_token` |
| code_challenge_methods | `S256`（PKCE） |
| token_endpoint_auth_methods | `client_secret_basic`, `client_secret_post`, **`none`** |
| scopes_supported | `openid` `profile` `email` **`offline_access`** |

两处值得注意：

1. `token_endpoint_auth_methods_supported` 含 **`none`** ⇒ 可以注册成 **public client**，只用 PKCE、
   **不需要 client_secret**。这正好对上我们代码里 `CHATCUT_OAUTH_CLIENT_ID` / `CHATCUT_OAUTH_CLIENT_SECRET`
   都是可选的行为。代码发的是 `client_secret_post`（凭据放在表单体里），与该服务器支持的方式一致。
2. `offline_access` 在 scope 列表里 ⇒ 这是**唯一能拿到 refresh_token 的开关**。不带它就只能拿到
   短期 access token，自动续期无从谈起。

### 凭证两种形态（实测的两条不同 401 文案）

| 请求 | 响应 |
|---|---|
| 不带 `Authorization` 头 | `Unauthorized: Authorization: Bearer <chatcut API key or JWT> is required` |
| 带了但 token 无效 | `Unauthorized: Invalid bearer token` |

⇒ **ChatCut 是先鉴权、后分发方法的**：未授权时任何方法（`tools/list` 也好、乱造的方法也好）
都回同一个 401。所以 **401 不能用来判断「工具名对不对」**，必须先让凭证有效再谈其他。

## 三、拿凭证的三条路（按省事程度排序）

### 路径 ①：静态 API Key —— **如果能找到入口，这是最优解**

ChatCut 自己的 401 文案写的是 `Bearer <chatcut API key or JWT>`，说明**它认 API Key 这种静态凭证**。
若你在账号后台能生成一个 API Key，那就：

```bash
CHATCUT_MCP_ACCESS_TOKEN="<那个 key>"
# 可选：标注过期时间，服务端会据此判失效
CHATCUT_MCP_ACCESS_TOKEN_EXPIRES_AT="2027-01-01T00:00:00Z"
```

完事。不需要 OAuth、不需要 client_id、不需要自动续期。

> ⚠ **我无法替你确认这个入口存不存在** —— 它需要登录 `app.chatcut.io`。
> 登录后找 **Settings / Developer / API Keys** 一类的页面。
> 找到就走这条；找不到再看路径 ③。

### 路径 ②：借官方宿主登录一次（Codex / Claude Code）

ChatCut 官方给的接入方式就是「宿主侧完成 OAuth」，安装指引页：

- Codex：`chatcut.io/chatgpt`
- Claude Code：`chatcut.io/claude`

装完登录一次，就能：

- ✅ 确认**账号本身可用**（这一步比什么都重要，见下面第四节）
- ✅ 拿到**真实的 `tools/list`**（工具名从这一刻起不再是猜的）

> ⚠ 但**别指望从这里把 refresh_token 搬走**：官方明确说「插件不接触密钥」，
> 凭据由宿主（Codex / Claude Code）托管在自己的凭据库里。这条路适合**验证**，
> 不适合**产出我们服务端要的长期凭证**。

### 路径 ③：自己走一次标准 OAuth —— **生产推荐，唯一能产出长期凭证的方式**

因为支持动态注册 + PKCE + public client，整条链路**不需要向 ChatCut 申请任何东西**，自助即可。

#### ★ 最快做法：一条命令（已实测到「就差你点一下」）

```bash
cd server
npm run chatcut:authorize              # 需要顺手写进 .env 就加 --write
```

脚本会把 PKCE 生成、动态注册 client、起本地回调服务器、用 code 换 token **全部自动做掉**，
**你只需要在弹出的浏览器里登录 ChatCut、点一次「同意」**。结束后它直接打印该加进 `.env` 的三行。

| 参数 | 作用 |
|---|---|
| `--write` | 顺手把三行写进 `server/.env`（该文件已被 `.gitignore` 忽略，不会进版本库） |
| `--no-open` | 不自动开浏览器，自己复制链接 |
| `--port 9000` | 换本地回调端口（会重新注册一个 client） |
| `--client-id xxx` | 复用已注册的 client（`redirect_uri` 必须与注册时一致） |

**如果一个字都不写就默认只打印、不落盘。** 没拿满 10 分钟收不到回调会自动放弃并释放端口。

**脚本内部把四个坑一次做对了**（手工做必踩）：

1. **`code_verifier` 先存好再用** —— 否则回来换 token 时报 `invalid_grant`，而 `code` 已经用掉了；
2. **`redirect_uri` 在授权与换 token 两次完全一致**；
3. **先起监听、再开浏览器** —— 否则用户点得比监听快会看到「无法访问此网站」，
   那一刻极易被误判成「回调地址没注册」，但其实只是监听还没起来；
4. **scope 里的空格编码成 `%20` 而不是 `+`** —— `URLSearchParams` 默认输出 `+`，
   而把 `+` 当字面量的实现会把它读成**一个** scope 名，于是 `offline_access` **静默失效**
   （表现是「授权成功了，但没有 refresh_token」）。ChatCut 的 authorize 又不校验参数完整性，
   这类错误不会当场报。

**已实测到哪一步**：用正确的 `state` + 假 `code` 回打本地回调，ChatCut 返回
`{"error":"invalid_grant","error_description":"invalid code"}` ——
说明**端点、请求格式、`code_verifier` 的传递全部正确**，
**唯一剩下的就是人工点一次同意**。同时也验证了 `state` 不匹配会被拒绝（防跨站伪造）。

#### 等价的手工做法（脚本已自动化，保留备查）

**a. 动态注册一个 client**

> ✅ **这一步 2026-09-17 已实测通过（HTTP 201）**，全链路无需登录、无需审批。下面这份 payload
> 就是实测用的那份。

```bash
curl -s -X POST 'https://api.chatcut.io/auth/mcp/register' \
  -H 'content-type: application/json' \
  -d '{
    "client_name": "dashuai-server",
    "redirect_uris": ["http://127.0.0.1:8765/callback"],
    "grant_types": ["authorization_code", "refresh_token"],
    "response_types": ["code"],
    "token_endpoint_auth_method": "none",
    "scope": "openid profile email offline_access"
  }'
```

已注册成功的返回：

```json
{"client_id":"MnCVZQAtqgQPxFksLKGYOAptmmpaMfDy","client_id_issued_at":1789631933,
 "redirect_uris":["http://127.0.0.1:8765/callback"],"token_endpoint_auth_method":"none",
 "grant_types":["authorization_code","refresh_token"],"response_types":["code"],
 "client_name":"dashuai-server","scope":"openid profile email offline_access"}
```

**你可以直接复用这个 `client_id`**（它绑定 `http://127.0.0.1:8765/callback`，是 public client、
没有 secret，本身不是机密）。想换回调地址就自己再注册一个 —— 注册是开放的。

> `redirect_uris` 只要是一个**你能收到回调**的地址即可。用 `127.0.0.1` 的本地端口最方便：
> 在你自己电脑上起一个临时监听，授权后浏览器会 302 回来带上 `code`。

**b. 浏览器里点一次同意（★ 这一步无头服务端做不了，必须人工）**

生成 PKCE 参数后拼出授权 URL：

```bash
# code_verifier 用 openssl 生成，code_challenge = BASE64URL(SHA256(code_verifier))
VERIFIER=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -binary -sha256 | openssl base64 | tr '+/' '-_' | tr -d '=')
echo "code_verifier  = $VERIFIER"     # ★ 先存下来，第 c 步要用
echo "code_challenge = $CHALLENGE"

echo "https://api.chatcut.io/auth/mcp/authorize?response_type=code&client_id=<client_id>&redirect_uri=http%3A%2F%2F127.0.0.1%3A8765%2Fcallback&scope=openid%20profile%20email%20offline_access&code_challenge=$CHALLENGE&code_challenge_method=S256"
```

> ✅ 这两条命令 2026-09-17 已实测：verifier 62 字符、challenge 43 字符（与标准写法交叉核对一致，
> RFC 7636 允许 43~128）。

把最后那行 URL 粘进浏览器 → 登录 ChatCut 账号 → 点同意 → 浏览器跳回
`http://127.0.0.1:8765/callback?code=xxxxx`，**从地址栏复制那个 `code`**（它很短命，通常几分钟）。

> ⚠ **实测发现：authorize 端点不校验参数完整性。** 用真实参数打会返回
> `302 → https://app.chatcut.io/authenticate?...`（参数原样透传）；而**故意漏掉 `code_challenge`
> 也照样 302**，不报错。
> ⇒ 这意味着**拼错的授权 URL 不会当场失败，只会走到一半才炸**（比如换 token 时报
> `invalid_grant`）。所以参数务必逐个核对，`code_verifier` 一定要先存好再往下走。

**c. 用 code 换 token**

```bash
curl -s -X POST 'https://api.chatcut.io/auth/mcp/token' \
  -H 'content-type: application/x-www-form-urlencoded' \
  -d 'grant_type=authorization_code' \
  -d 'code=<上一步的 code>' \
  -d 'redirect_uri=http://127.0.0.1:8765/callback' \
  -d 'client_id=<client_id>' \
  -d "code_verifier=$VERIFIER"
```

返回里同时有 `access_token` 和 **`refresh_token`** —— 我们只要后者。

**d. 填进 `.env`**

```bash
CHATCUT_OAUTH_TOKEN_URL="https://api.chatcut.io/auth/mcp/token"
CHATCUT_OAUTH_REFRESH_TOKEN="<上一步的 refresh_token>"
CHATCUT_OAUTH_CLIENT_ID="<client_id>"
# public client 没有 secret，CHATCUT_OAUTH_CLIENT_SECRET 留空
```

## 六、两个必须现场验证的代码假设

探测器会直接把这两件事的结论打出来 —— **如果它们是错的，那问题不是填 `.env` 能解决的，必须改代码**：

1. **`initialize` 握手。** `src/render/chatcut.ts::rpc()` **从不发 `initialize`**，直接 POST `tools/list`。
   多数 MCP server 允许这样，但规范并不保证（有的要求先握手拿 session id）。
   若 ChatCut 要求握手，症状会是「探针说通道正常、线上 AI 档却一直失败」。
2. **入参 schema。** `submitChatCutJob()` 发的是一个固定形状的大对象
   （`idempotencyKey / projectName / source / keywords / render / voice / captions / audio / editing / clips`），
   `getChatCutJob()` 发 `{ jobId }`。若 ChatCut 真实工具的参数名对不上，就得改 `chatcut.ts` 去适配。
   探测器会把「我们发但工具不认的字段」逐个列出来。

## 七、安全纪律

- `CHATCUT_OAUTH_REFRESH_TOKEN` / `CHATCUT_MCP_ACCESS_TOKEN` / `CHATCUT_OAUTH_CLIENT_SECRET`
  **只放服务端环境**，绝不提交到 Git（**本仓库是 public**），也不写入小程序、日志。
- `refresh_token` 会轮换：`chatcut.ts` 已实现「服务端存回 Redis 的新 refresh_token 优先于环境变量」，
  所以偶尔会看到「Redis 里的 token 和 `.env` 里的不一样」—— **这是正常的**，不要去改 `.env` 对齐。
- 服务端已有 Redis 分布式锁 + 进程内 single-flight 防并发刷新，**同一账号可安全多实例部署**。
