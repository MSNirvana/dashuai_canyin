## 一、配成了什么

三个通道，统一 `baseUrl = https://tokenbox.you/v1`、协议 `OPENAI_COMPATIBLE`：

| 顺序 | 供应商 code | 模型 | 用途 |
|---|---|---|---|
| 主 | `tokenbox-gpt` | `gpt-5.5` | 首选 |
| 备 1 | `tokenbox-claude` | `claude-sonnet-5` | 主不可用时自动顶上 |
| 备 2 | `tokenbox-deepseek` | `deepseek-v4-flash` | 前两个都不可用时兜底 |

**11 个 AI 场景**全部指向这条链（`ai_scene.default_model_id` + `fallback_model_ids`）。
历史上的 `mock-local`、旧 `deepseek`、以及中途试过的 `gpt-5.6-sol` 中转供应商**已停用但不删除**
（`ai_call_log.provider_id` 有外键，删了会连带清掉调用历史）。

### 「自动备用」是怎么成立的

**失败转移顺序由 `ai_scene` 的候选数组决定，不是 `ai_provider.priority`**
（priority 只影响后台列表排序）。网关按 `[defaultModelId, ...fallbackModelIds]` 依次尝试：

- 通道被熔断 / `healthStatus=DOWN` / `enabled=false` / 超预算 → **直接跳过**
- 通道级硬故障（超时 / 连不上 / HTTP 401 / 403 / 429 / 5xx）→ **立即熔断 60s** 并放弃该通道剩余重试
- 熔断是 Redis 里一个 TTL=60s 的 key，到期自动消失 → 下次请求重新试主通道
  ⇒ **「恢复后自动切回来」天然成立，不需要额外代码，也没有粘性状态**

### 本轮补的那一半（原来只有一半）

原实现**只靠失败率熔断**跳坏通道，而它要求滑动窗口内至少 `minSamples=20` 个样本。
低频场景（如 `copy_intro` 一天几次）几小时都攒不满 20 个，于是每个请求都要先在坏通道上
干等一次 `ai_scene.timeout_ms`（默认 30s）才轮到备用 ——「自动切换」名义上有、体验上没有。

现在加了 `isChannelLevelFailure()`：**通道级硬故障当场熔断 + 放弃剩余重试**，直接换下一个候选。

## 二、模型怎么选的（实测，不是拍脑袋）

用真实 `copy_intro` 提示词（80~150 字中文文案、`max_tokens` 800）各打 3 次：

| 模型 | 成功 | 耗时(秒) | 结论 |
|---|---|---|---|
| `gpt-5.4` | 0/3 | 400 / 超时 | 不可用 |
| `gpt-5.6-terra` | 2/3 | 36.1 / 7.4 / 60✗ | 尾部超时风险高 |
| `gpt-5.6-luna` | 2/3 | 25.9 / 32.4 / 45✗ | 太慢 |
| `gpt-5.6-sol` | 3/3 | 37.6 / 35.7 / 8.4 | 延迟双峰（8s 或 36s+） |
| `gpt-6-astra` | 2/3 | 4.0 / 6.9 / 45✗ | 尾部超时风险高 |
| **`gpt-5.5`** | **3/3** | **9.1 / 8.9 / 8.6** | **稳，选它** |
| **`claude-sonnet-5`** | **3/3** | **5.6 / 5.5 / 5.5** | **稳且最快** |
| `claude-haiku-4-5` | 3/3 | 1.9 / 2.4 / 2.1 | 备选（但对大输出不胜任，见下） |
| `deepseek-v4-pro` | 3/3 | 38.9 / 9.3 / 41.8 | 慢，且单次 2000+ token |
| **`deepseek-v4-flash`** | **3/3** | **4.2 / 4.2 / 4.2** | **稳且快，选它** |

**原则**：三个模型都要稳稳落在 `ai_scene.timeout_ms` 之内，否则「正常的慢」会被当成故障，

## 三、顺带修掉的两个真实缺陷

### ① 空正文被当成「成功」，照常扣豆

**成因**：tokenbox（以及不少厂商）把 `max_tokens` 同时当作「思考(reasoning) + 正文」的总预算。
三个候选通道都是推理模型，实测同一提示词、`max_tokens=800`：

| 模型 | 情况 |
|---|---|
| `gpt-5.5` | reasoning 188~352 token，正文正常（completion 404~714，已逼近 800） |
| `claude-sonnet-5` | 一般正常，但实测出现过一次 `finish_reason=length` + 正文为空 |
| `claude-haiku-4-5` | **3/3 把 800 全花在思考上 → `finish_reason=length`、正文 = `''`** |
| `deepseek-v4-flash` | reasoning 仅 40~50，正常 |

「正文为空」时 **HTTP 仍是 200、报文结构完全合法**。原适配器只校验
「`content` 是字符串」→ 空字符串通过 → 网关判成功 → `ai.service` 照常扣豆、把空文案交给商户。

**修法**（`src/ai/adapters.ts`）：空白正文抛 `BAD_RESPONSE`。
于是它会被当成失败：本通道按 `maxRetries` 重试 → 仍失败则**转入下一个候选通道** →
全部失败才回落 `ai_scene.fallback_template` 且**不扣豆**（这是项目铁律）。

### ② 场景的 `max_output_tokens` 是按「非推理模型」定的

11 个场景原值：`title_overlay` / `bgm_select` 300、`review_guard` 400、`rhythm_detect` 500、
`script_polish` 600、copy 系 800、`storyboard_generate` 2500。配上会思考的推理模型后，
小场景的预算会被思考**吃光 → 正文返回空**。

**修法**：`setup-ai-channels.ts` 把全部场景抬到 **≥ 4000 token（只抬不降）**。
抬高上限**不强制多花 token**（模型该花多少花多少），只是不再被截断。

## 四、`storyboard_generate` 的单独覆盖（重要）

它是唯一的「大输出」场景（6~8 个分镜、1000+ token JSON），三个通道实测差异极大
（真实提示词，含 425 字镜头库）：

| 通道 | 结果 |
|---|---|
| `gpt-5.5` | ✓ 21.7s，1715 字，8 个分镜 |
| `deepseek-v4-flash` | ✓ 46.4s，1381 字，7 个分镜（**超过默认 40s**） |
| `claude-sonnet-5` | ✗ 105s 且最终**空正文** —— 完全不胜任 |

所以对它单独做了两处覆盖：

1. **备用顺序调成 `[DeepSeek, Claude]`** —— 否则 Claude 会先干等一次超时（最坏 90s）再轮
2. **`timeout_ms` 放宽到 90s** —— 40s 装不下 DeepSeek 的 46s

不改的话：**GPT 上游一挂，storyboard 只能回落 3 分镜兜底模板**。

## 五、⚠ 计费核查：「成本 × 系数」这条链路**当前没有真正生效**

> 起因：2026-09-15 用户提出「用户针对 AI 的使用，是要按照实际调用成本 ✖️ 设定系数来扣积分的，
> 这个我之前就设定过，你看一下目前是不是这样」。以下是核实结果。

### 结论一句话

**代码链路确实就是「成本 × 系数」（系数也在库里），但当前并没有生效** ——
模型单价是 0 ⇒ 成本恒为 0 ⇒ 扣 0 豆；而且就算补上单价，**11/11 个场景的单次上限都会把它截断**。

### 计费链路（已逐行核实，`src/ai/ai.service.ts`）

```
costFen  = ceil(promptTok × input_price_per_mtok  / 1e6)
         + ceil(completionTok × output_price_per_mtok / 1e6)        ← 单位：分
want     = ceil(costFen × points_per_yuan × cost_multiplier / 100)  ← 单位：豆
charged  = min(want, ai_scene.bean_price)   ← bean_price 同时是「预冻结额」和「单次硬上限」
absorbed = want − charged                   ← 平台承担，落库 + console.warn
```

系数确实都在库里（已查询确认）：

| 设置项 | 值 | 含义 |
|---|---|---|
| `charge_mode` | `COST_BASED` | 计费模式 |
| `cost_multiplier` | `4` | AI 成本系数 |
| `points_per_yuan` | `100` | 1 元 = 100 豆 |
| `register_grant_points` | `30` | 注册赠豆 |

⇒ 即「1 分成本 = 4 豆」，**与「成本 × 系数」完全一致，这部分没问题**。

### 断点 ①：模型单价是 0 ⇒ 永远扣 0 豆

```
tokenbox-gpt        gpt-5.5             in=0  out=0    分/百万 token
tokenbox-claude     claude-sonnet-5     in=0  out=0
tokenbox-deepseek   deepseek-v4-flash   in=0  out=0
```

`beansFromCost()` 第 45 行：`if (costFen === 0) return 0n` ⇒ **零成本调用，全额释放冻结豆**。

**库里的实测证据**（`ai_call_log`，近 24h 真实调用）：

```
storyboard_generate   tok=726/5308    cost=0分  charged=0豆  absorbed=0
storyboard_generate   tok=1106/1496   cost=0分  charged=0豆  absorbed=0
storyboard_generate   tok=527/3017    cost=0分  charged=0豆  absorbed=0
```

一次吃掉 **5308 个输出 token** 的调用同样 `charged=0` —— 不是「成本太小所以显示 0」，是**压根没在算**。

### 断点 ②：11/11 个场景的单次上限都会截断真实成本

`bean_price` 现值是 3 / 5 / 10 豆，而真实成本换算出来是 20~123 豆。
`charged = min(want, frozenAmount)` ⇒ 实际扣费变成**封顶值**，而不是「成本 × 系数」。

### ⚠ 抬上限引入的连带回归：新用户「一个 AI 功能都用不了」

上限同时是**预冻结额**，抬上去后「账户可用豆不足」的门槛也一起抬高。
注册赠豆原本只有 30，而上限抬到 40~250 后 **11/11 个场景的上限都 > 30** ⇒
新用户注册后**不是「扣得少」，而是冻结阶段直接被拦**：

```
BeanNotEnoughError: AI豆不足：需要 80，可用 30
  at bean.service.ts:193 freeze
  at ai.service.ts:145 runBilledScene
```

这是本次实测**当场复现**的（用商户 3 跑 `copy_intro` 时报的就是这个错）。
先后落地的两个修法：

1. `TB_REGISTER_GRANT=600`（当日早先）：60 万豆 = 平台成本约 ¥1.5/人，
   够新用户跑通 4 次分镜 或 15 次文案，完整体验一轮再决定付费。
2. **`TB_REGISTER_GRANT=0`（当日最终）**：产品决定取消新用户免费赠送，
   改为「注册后必须购买 ¥980 会员」。此时赠豆 0 与会员闸门**同时拦**，
   用户看到的是统一的「需要订阅后才能使用该功能」，而不是「有积分却生成不了」。

> **教训**：把「预冻结额」和「单次扣费上限」用同一个字段实现，会让
> 「给平台留财务安全网」和「让新用户能上手」变成一对矛盾。
> 改其中一个必须同时看另一个。脚本的 `[4/6]` 步骤现在会直接打印
> 「注册赠豆 vs 最贵场景上限 ⇒ 新用户可用的场景 N/11」把这个矛盾摆到台面上；
> 当赠豆为 0 时改为提示「这是策略（必须先买会员），不是故障」，避免下次误判成配错。

### ★ 单次成本能差 15 倍，变量是「思考 token」不是文案长度

同一提示词、同一通道（`claude-sonnet-5`）连打 3 次：

| # | 输入 tok | 输出 tok | 成本 | 应扣豆 | 耗时 | 文案长度 |
|---|---|---|---|---|---|---|
| 1 | 433 | 171 | **5 分** | 20 豆 | 6.9s | 126 字 |
| 2 | 433 | **1979** | **31 分** | 124 豆 | 54.7s | 130 字 |
| 3 | 334(deepseek) | 132 | **2 分** | 8 豆 | 33.4s | 97 字 |

正文都是 100~130 字，**成本差 15 倍**。三个推论：

1. **按字数/按次定价会亏** —— 必须按 token 成本算（本项目就是这么做的）。
2. **场景上限只能是财务安全网，不能当常规定价用** —— 它一定会被周期性击穿
   （上表 #2 就击穿了 80 豆的上限，平台承担 44 豆）。击穿部分记 `absorbedBeans`，是设计如此。
3. **失败重试的 token 不计费也不入账**（只记最终成功那次），但那部分钱平台仍付给了上游。

## 六、怎么操作

### 本地（已完成，可重复跑，幂等）

```bash
cd server
TB_GPT_KEY=sk-xxx TB_CLAUDE_KEY=sk-xxx TB_DEEPSEEK_KEY=sk-xxx \
  npx tsx scripts/setup-ai-channels.ts        # 或 npm run ai-channels:setup
```

Key 一律从环境变量读（**本仓库是 public，绝不写进代码**）。可用的环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `TB_GPT_KEY` / `TB_CLAUDE_KEY` / `TB_DEEPSEEK_KEY` | 必填 | 三个统一 Key |
| `TB_GPT_MODEL` / `TB_CLAUDE_MODEL` / `TB_DEEPSEEK_MODEL` | `gpt-5.5` / `claude-sonnet-5` / `deepseek-v4-flash` | 换模型不用改代码 |
| `SCENE_MIN_OUTPUT_TOKENS` | `4000` | 场景输出预算下限（只抬不降） |
| `TB_SET_PRICES` | 未设（=不写单价） | 设 `1` 才把真实单价写库 ⇒ **AI 开始按成本扣豆** |
| `TB_SET_CAPS` | 未设（=不写上限） | 设 `1` 才把场景单次上限抬到不截断的水平 |
| `TB_REGISTER_GRANT` | 未设（=不改） | 注册赠豆，如 `0`（当前值 = 关闭赠送）或 `600`。**只影响新注册**，老用户不受影响 |
| `TB_USD_TO_CNY` | `7.2` | 汇率（tokenbox 按美元计费，本仓库按人民币「分」记账） |

> ⚠ **只改商业参数也得带三个 Key**：商业参数步骤排在通道配置之后，而通道配置强制要求
> `TB_*_KEY` ⇒ 只想把 `register_grant_points` 从 600 改成 0，也得把密钥一起带上。
> 不想带密钥时走**后台【系统配置】页**（分组 `bean`，`Settings.tsx`）直接改，
> 该路由会 `invalidate()` 清配置缓存；或用一个只改这一行的临时脚本。

脚本做六件事（幂等，可重复跑）：

1. 按 code upsert 三个供应商（统一 `baseUrl`）
2. 重建 11 个场景的候选链（含 `storyboard_generate` 的单独覆盖）

4. **商业参数对照 / 应用**：场景单次上限（`TB_SET_CAPS=1`）+ 注册赠豆（`TB_REGISTER_GRANT=n`），
   并打印「注册赠豆 vs 最贵场景上限 ⇒ 新用户可用的场景 N/11」

### 观察到的上游抖动（非我方问题）

- 配好当天 `tokenbox-gpt` 上游出现过一段 **HTTP 401 `User account is not active`**
  （3/3 复现，约十几分钟后自行恢复）—— 这是 tokenbox「Gpt pro号池」侧的状态，
  同一 Key 的 `/v1/models` 与 `/api/pricing` 始终 200，说明 **Key 有效、是上游账户不可用**。
  ⇒ 网关会把它判为通道级故障、立即熔断并切到 Claude（这就是「自动备用」的真实演练）。
- GPT 池整体约 1/3 请求会挂到 45s+（尾部延迟）。所以后台「测试」按钮偶尔会报 GPT 失败，
  那不代表配置错。`verify-ai-failover` 的第 ⑧ 项因此把闸门定为「**至少一条通道可用**」。
- **重配通道后记得清熔断 key**（`ai:cb:open:<providerId>`，TTL 60s）。
  不清的话会有最长 60s 的「明明配好了、请求还是走备用」窗口。配置脚本已内置清理。
