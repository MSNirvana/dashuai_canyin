## 一、配成了什么

三个通道，统一 `baseUrl = https://tokenbox.you/v1`、协议 `OPENAI_COMPATIBLE`：

| 顺序 | 供应商 code | 模型 | 用途 |
|---|---|---|---|
| 主 | `tokenbox-gpt` | `gpt-5.5` | 首选 |
| 备 1 | `tokenbox-claude` | `claude-sonnet-5` | 主不可用时自动顶上 |
| 备 2 | `tokenbox-deepseek` | `deepseek-v4-flash` | 前两个都不可用时兜底 |

**11 个 AI 场景**全部指向这条链（`ai_scene.default_model_id` + `fallback_model_ids`）。
历史上的 `mock-local`、旧 `deepseek`、以及中途试过的 `gpt-5.6-sol` 中转供应商**已停用但不删除**
（`ai_call_log.provider_id` 有外键，删了会连带清掉调用历史）。

### 「自动备用」是怎么成立的

**失败转移顺序由 `ai_scene` 的候选数组决定，不是 `ai_provider.priority`**
（priority 只影响后台列表排序）。网关按 `[defaultModelId, ...fallbackModelIds]` 依次尝试：

- 通道被熔断 / `healthStatus=DOWN` / `enabled=false` / 超预算 → **直接跳过**
- 通道级硬故障（超时 / 连不上 / HTTP 401 / 403 / 429 / 5xx）→ **立即熔断 60s** 并放弃该通道剩余重试
- 熔断是 Redis 里一个 TTL=60s 的 key，到期自动消失 → 下次请求重新试主通道
  ⇒ **「恢复后自动切回来」天然成立，不需要额外代码，也没有粘性状态**

### 本轮补的那一半（原来只有一半）

原实现**只靠失败率熔断**跳坏通道，而它要求滑动窗口内至少 `minSamples=20` 个样本。
低频场景（如 `copy_intro` 一天几次）几小时都攒不满 20 个，于是每个请求都要先在坏通道上
干等一次 `ai_scene.timeout_ms`（默认 30s）才轮到备用 ——「自动切换」名义上有、体验上没有。

现在加了 `isChannelLevelFailure()`：**通道级硬故障当场熔断 + 放弃剩余重试**，直接换下一个候选。

## 二、模型怎么选的（实测，不是拍脑袋）

用真实 `copy_intro` 提示词（80~150 字中文文案、`max_tokens` 800）各打 3 次：

| 模型 | 成功 | 耗时(秒) | 结论 |
|---|---|---|---|
| `gpt-5.4` | 0/3 | 400 / 超时 | 不可用 |
| `gpt-5.6-terra` | 2/3 | 36.1 / 7.4 / 60✗ | 尾部超时风险高 |
| `gpt-5.6-luna` | 2/3 | 25.9 / 32.4 / 45✗ | 太慢 |
| `gpt-5.6-sol` | 3/3 | 37.6 / 35.7 / 8.4 | 延迟双峰（8s 或 36s+） |
| `gpt-6-astra` | 2/3 | 4.0 / 6.9 / 45✗ | 尾部超时风险高 |
| **`gpt-5.5`** | **3/3** | **9.1 / 8.9 / 8.6** | **稳，选它** |
| **`claude-sonnet-5`** | **3/3** | **5.6 / 5.5 / 5.5** | **稳且最快** |
| `claude-haiku-4-5` | 3/3 | 1.9 / 2.4 / 2.1 | 备选（但对大输出不胜任，见下） |
| `deepseek-v4-pro` | 3/3 | 38.9 / 9.3 / 41.8 | 慢，且单次 2000+ token |
| **`deepseek-v4-flash`** | **3/3** | **4.2 / 4.2 / 4.2** | **稳且快，选它** |

**原则**：三个模型都要稳稳落在 `ai_scene.timeout_ms` 之内，否则「正常的慢」会被当成故障，
无谓触发故障转移、白白多等一次超时。`gpt-5.6-sol` 就是反例（1/3 概率 36s > 30s 超时线）。

## 三、顺带修掉的两个真实缺陷

### ① 空正文被当成「成功」，照常扣豆

**成因**：tokenbox（以及不少厂商）把 `max_tokens` 同时当作「思考(reasoning) + 正文」的总预算。
三个候选通道都是推理模型，实测同一提示词、`max_tokens=800`：

| 模型 | 情况 |
|---|---|
| `gpt-5.5` | reasoning 188~352 token，正文正常（completion 404~714，已逼近 800） |
| `claude-sonnet-5` | 一般正常，但实测出现过一次 `finish_reason=length` + 正文为空 |
| `claude-haiku-4-5` | **3/3 把 800 全花在思考上 → `finish_reason=length`、正文 = `''`** |
| `deepseek-v4-flash` | reasoning 仅 40~50，正常 |

「正文为空」时 **HTTP 仍是 200、报文结构完全合法**。原适配器只校验
「`content` 是字符串」→ 空字符串通过 → 网关判成功 → `ai.service` 照常扣豆、把空文案交给商户。

**修法**（`src/ai/adapters.ts`）：空白正文抛 `BAD_RESPONSE`。
于是它会被当成失败：本通道按 `maxRetries` 重试 → 仍失败则**转入下一个候选通道** →
全部失败才回落 `ai_scene.fallback_template` 且**不扣豆**（这是项目铁律）。

### ② 场景的 `max_output_tokens` 是按「非推理模型」定的

11 个场景原值：`title_overlay` / `bgm_select` 300、`review_guard` 400、`rhythm_detect` 500、
`script_polish` 600、copy 系 800、`storyboard_generate` 2500。配上会思考的推理模型后，
小场景的预算会被思考**吃光 → 正文返回空**。

**修法**：`setup-ai-channels.ts` 把全部场景抬到 **≥ 4000 token（只抬不降）**。
抬高上限**不强制多花 token**（模型该花多少花多少），只是不再被截断。

## 四、`storyboard_generate` 的单独覆盖（重要）

它是唯一的「大输出」场景（6~8 个分镜、1000+ token JSON），三个通道实测差异极大
（真实提示词，含 425 字镜头库）：

| 通道 | 结果 |
|---|---|
| `gpt-5.5` | ✓ 21.7s，1715 字，8 个分镜 |
| `deepseek-v4-flash` | ✓ 46.4s，1381 字，7 个分镜（**超过默认 40s**） |
| `claude-sonnet-5` | ✗ 105s 且最终**空正文** —— 完全不胜任 |

所以对它单独做了两处覆盖：

1. **备用顺序调成 `[DeepSeek, Claude]`** —— 否则 Claude 会先干等一次超时（最坏 90s）再轮
2. **`timeout_ms` 放宽到 90s** —— 40s 装不下 DeepSeek 的 46s

不改的话：**GPT 上游一挂，storyboard 只能回落 3 分镜兜底模板**。

## 五、⚠ 两件待你拍板的事

### 1. 单价仍未写库 ⇒ AI 目前对商户完全免费

计费口径是「按实际成本扣豆」：`ai_call_log.cost_fen` → 豆，并受场景单次上限（5/10/3 豆）约束。
模型单价现在是 **0** ⇒ `cost_fen = 0` ⇒ 走「零成本调用，全额释放」⇒ **商户扣 0 豆**。

真实单价已从 `GET https://tokenbox.you/api/pricing` 反推出来（tokenbox 是 NewAPI 系）：

```
美元成本 = tokens × 系数 × group_ratio ÷ 500000          ← NewAPI 约定 500000 quota = $1
```

| 模型 | 输入 $/Mtok | 输出 $/Mtok | 依据 |
|---|---|---|---|
| `gpt-5.5` | 4.0 | 24.0 | `p×5 c×30`，分组「Gpt pro号池」×0.4 |
| `claude-sonnet-5` | 4.0 | 20.0 | ratio 1 / completion 5，分组「Claude max」×2 |
| `deepseek-v4-flash` | 1.2 | 4.8 | `p×1 c×4`，分组「Deepseek官方」×0.6（**空闲时段**） |

> ⚠ DeepSeek 分时定价：9:00-12:00 与 14:00-18:00 **翻倍**；上表是空闲时段价。
> ⚠ 这些数字请对照你自己 tokenbox 控制台的账单再核一遍。

写库后会怎样：一次 `copy_intro` 约 40 豆成本，但单次上限只有 5 豆
⇒ `ai.service` 会把超出的 35 豆记为「平台承担」并打告警日志。
**上限是否上调属于给用户涨价，是商业决策**（这一点在项目长期约定里也标着「待拍板」）。

所以脚本**默认不写单价**，只打印；确认后 `TB_SET_PRICES=1` 重跑即可。

## 六、怎么操作

### 本地（已完成，可重复跑，幂等）

```bash
cd server
TB_GPT_KEY=sk-xxx TB_CLAUDE_KEY=sk-xxx TB_DEEPSEEK_KEY=sk-xxx \
  npx tsx scripts/setup-ai-channels.ts        # 或 npm run ai-channels:setup
```

Key 一律从环境变量读（**本仓库是 public，绝不写进代码**）。可用的环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `TB_GPT_KEY` / `TB_CLAUDE_KEY` / `TB_DEEPSEEK_KEY` | 必填 | 三个统一 Key |
| `TB_GPT_MODEL` / `TB_CLAUDE_MODEL` / `TB_DEEPSEEK_MODEL` | `gpt-5.5` / `claude-sonnet-5` / `deepseek-v4-flash` | 换模型不用改代码 |
| `SCENE_MIN_OUTPUT_TOKENS` | `4000` | 场景输出预算下限（只抬不降） |
| `TB_SET_PRICES` | 未设（=不写单价） | 设 `1` 才把真实单价写库 |
| `TB_USD_TO_CNY` | `7.2` | 汇率 |

脚本做五件事：配置三个供应商 → 重建 11 个场景的候选链 → 抬高输出预算 →
停用历史供应商 → 清熔断状态并打印生效配置 + 解密自检。

### 验证

```bash
cd server
npm run ai-failover:verify                    # 43 项断言，全绿
SKIP_LIVE=1 npm run ai-failover:verify        # 跳过真实调用
```

覆盖：判定矩阵、生产配置核对（含 storyboard 例外）、主通道挂掉落备用且**不白等重试**、
熔断期内跳过坏通道、熔断到期自动切回、**候选顺序与 priority 无关**、
**空正文必须触发故障转移**、三个真实通道冒烟、熔断器参数回归。

### 服务器

```bash
# ① 本地编译 + 同步（README 有完整命令）
cd server && npm run build
rsync -az ... server/dist/ ubuntu@49.232.243.241:/opt/dashuai/server/dist/
rsync -az ... server/scripts/ ubuntu@49.232.243.241:/opt/dashuai/server/scripts/

# ② 在服务器上跑配置脚本（Key 用环境变量传，别落盘）
ssh ubuntu@49.232.243.241
cd /opt/dashuai/server
TB_GPT_KEY=... TB_CLAUDE_KEY=... TB_DEEPSEEK_KEY=... npx tsx scripts/setup-ai-channels.ts

# ③ 重启并验证
pm2 restart dashuai-api
curl -s http://127.0.0.1:3000/healthz
```

> 不重启 = 跑的还是旧代码（本项目已因此被误导过一次）。

## 七、实测记录

### `npm run ai-failover:verify` — 43 通过 / 0 失败

关键几条：

```
③ 总尝试次数 = 2（坏通道仅 1 次，未耗尽重试）      ← 「立即熔断 + break」生效
   坏通道已被立即熔断（不等攒满 20 个样本）
   熔断 key 的 TTL ≤ openSeconds(60s)  ttl=60s
④ 总尝试次数 = 1（主通道被跳过，没白等）
⑤ 又去试了主通道（attempts=2）⇒ 到期自动切回
⑦ 空正文被识别为失败 → 转入备用通道；最终正文非空 82 字
```

### 产品层端到端（走 `runBilledScene`，含真实冻结/结算/解冻）— 12 通过 / 0 失败

| 用例 | 结果 |
|---|---|
| `copy_intro` 正常 | 12.3s，95 字，走主通道 GPT，非兜底模板 |
| `storyboard_generate` | 2473 字，**12 个分镜**，非兜底模板 |
| 主通道指向黑洞 | 6.4s，自动切 Claude，非空文案，日志 `FALLBACK_USED` |
| 账户基线 | 跑完与基线逐字段一致（balance / grantBalance / grantRegister / frozen） |

### 观察到的上游抖动（非我方问题）

- 配好当天 `tokenbox-gpt` 上游出现过一段 **HTTP 401 `User account is not active`**
  （3/3 复现，约十几分钟后自行恢复）—— 这是 tokenbox「Gpt pro号池」侧的状态，
  同一 Key 的 `/v1/models` 始终 200，说明 **Key 有效、是上游账户不可用**。
  ⇒ 网关会把它判为通道级故障、立即熔断并切到 Claude（这就是「自动备用」的真实演练）。
- GPT 池整体约 1/3 请求会挂到 45s+（尾部延迟）。所以后台「测试」按钮偶尔会报 GPT 失败，
  那不代表配置错。`verify-ai-failover` 的第 ⑧ 项因此把闸门放宽为「**至少一条通道可用**」。
